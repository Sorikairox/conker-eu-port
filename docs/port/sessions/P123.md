## 1. Root cause: the menu scene starts black and the fade-in event runs in a stub

Chain (node, `?p103boot=1&p121spr=1`, new `?p123tri=N` / `?p123fade=1` logs):

1. The DL is nearly empty on the menu, not culled: from frame 2141, 114 commands and 0 triangles per task (3121+: 347
   commands), against 1300..1500 commands and 1347 triangles in the LogoScreen scene. The `?dltrace=600` dump holds
   only the viewports, matrices, lights and a black fill rectangle: **no world or object DL is called**. So the
   renderer is fine. The game C skips the draw.
2. `?p123noscene=1` (TEST ONLY: skip func_1501D348 in mode 3, as when func_151DEDD0 was a stub in P116) brings the 3D
   back (task 540: 2059 commands, 1165 triangles). So the cause is **the menu level's scene 1 starting**, which P117's C
   menu handler func_151DEDD0 now does on its first mode-3 frame (D_80090120 branch). P116 never started it. That is
   why P116 drew the room.
3. The world draws in func_15019464 / func_150195A0 (game_45B80.c) return early when `func_1517F51C(player)` is set,
   i.e. the screen fade level func_1517F470(0) == 0xFF (fully black). Gate probe (`?p123fade=1`): from 2139 to the end of
   the run, **fade level 255 (dir 1, timer 0/0)**. D_800BEAC0, D_80084810 and D_800D18A0 stay 0.
4. Who set it: `func_1517F3B0(0, 0, 0, 0 frames, dir 1, 0)` at frame 2139 from **func_1501DB18** (scene start, C). It
   takes the earliest 5/0x01 event of the scene: level 0x1D scene 1, track 0, t = 0 `5/0x01 b4 0 b5 0 w6 1` (scdis).
   In the LogoScreen scene the same call has dir 0 (visible), so it never showed there.
5. The fade-in is the same event processed by the scene handlers: type 5 id 1 is **not** handled by A (func_15024910)
   or B (func_150268BC). It is handled by **handler C func_15029EA8** (game_eu_51190.c, still `#pragma GLOBAL_ASM`, a
   port stub), EU asm 1502A61C..1502A79C:
   - `b4 == 0`: `d = arg9 ? 0 : func_15023C60(ev, 5, track, &tmp, 1, 1, 0, 0, 0, 0, player) - now` (time to the next
     5/1 event), then `func_1517F3B0(D_800844A0[b5][0], [1], [2], d, w6 == 0, 0)` and `D_800C40AA = (w6 == 0)`; return 1.
   - `b4 != 0` and arg9 (skip mode): look back with func_15023EC4 for the previous 5/1 and set its colour at once
     (frames 0); return 1.
   With the stub the fade never starts: black screen, no world draw, for the whole menu.

**Fix (game C, for a conversion slot):** convert func_15029EA8 (game_eu_51190.c, 891 asm lines). Its type 5 id 1
branch (above) is the part the menu needs. Producers before consumers: it also handles types 6 / 0xA (sounds:

func_1000DE1C), func_1505E650, func_15023EC4 and func_1503DE70. Check them with `port/tools/stubcalls.py --func func_15029EA8`.

## 4. Scene-end camera retarget (P113 guard, 3053 case): reading only

- **No scene event retargets camera 0 +0x3D4.** Scene type 3 (handler A, C) only switches the scene's camera *track*
  (`D_800C3A18 = id` when the ref kind is 1 and the id differs; D_800DBFF4[0] = 4 (snap counter, decremented per frame
  in game_14FF90), camera +0x5F0 |= 4). Level 0x1D scene 1 ends with `t = 1100 3/0x0` = track 0, the one already used,
  so it does nothing. LogoScreen's 3/0xD is the same kind.
- +0x3D4 is written only by the camera init: `func_1512868C` (game_14FF90.c line 2461, C):
  `unk3D0 = &D_800CC2D0[unk23D]; unk3D4 = unk3D0->unk31C`, and the asm init func_150054C4 (game_32740, called per
  camera from game_32740.c line 44). func_1512868C is called from game_eu_EC560.c line 21 and from the asm
  func_15097188 (game_eu_C4590, beside the event natives func_15096DB0 / func_15096E78; it also sets D_800DBFF4) and
  func_150BED50.
- The removed object 105DF6F0 is **D_800CC2D0[0] itself** (slot 4 = 105E03A0 - 4 * 0x32C). func_1501DF70 (scene end)
  calls `func_15060F28(func_15072208(D_800CC2D0, 0), 0)`, which frees slot 0's +0x31C record while camera 0 still points
  at it. On N64 nothing re-targets it either. Best guess (UNVERIFIED): the N64 survives because the record's memory is
  reused for the next slot-0 record, or because the write in func_15122AE0 lands harmlessly on the N64 heap. The port
  needs either the next camera init (func_1512868C via func_15097188 / func_150054C4 when the level or player respawns)
  or the guard. Next step: log which of func_1512868C / func_150054C4 / func_15097188 run after 2133 and after 3053 in a
  boot without the guard, and compare D_800CC2D0[0]+0x31C before and after.
