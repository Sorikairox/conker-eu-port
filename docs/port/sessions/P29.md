### A regression the merge exposed, fixed in gen_stubs.py

After the merge the frame DL fell from 175 to **12 commands** (prefix only). `gdltrack=240` showed the DL
pointer turning into `0xC8` between `func_1517485C` and `func_15186D04`, which is inside the now-C
**func_1510BF50**:

```c
gdl = func_150A5858(D_800B0E00[0], gdl, (u8 *)D_800DA030[player], 0, 0, mask);
```

func_150A5858 is still asm, and its **DL pointer is the second argument**. The stub returned
`port_stub_dlret(a0)` = 0, because `a0` (a DL address) is not in the frame buffers. The frame then ran past
its buffer and `func_eu_1501C860` dropped it.

**Fix** (`port/tools/gen_stubs.py`): a function declared `Gfx *f(T, Gfx *, ...)` with its first `Gfx *`
parameter at index k > 0 gets a stub that returns `a{k}` (tag `:passthruK`). Only func_150A5858 qualifies
today (`passthru1`).

## 3. Runtime check of func_15110420's callback (P28 UNVERIFIED)

The C site is `game_eu_13DC30.c:104`:

```c
gdl = D_80089578[D_800B0DF0->unk8](gdl, x, y, z, yaw, pitch, roll, handle);
```

- **Site type.** The pointer type is `Gfx *(*)(Gfx *, f32 ×6, s32)`, which is the wasm site `i:iffffffi`.
- **Matches the asm.** The asm (`func_15110420.s`, 0x151107CC..0x151107FC) passes:
  - `a1 = x`, `a2 = y`, `a3 = z` as float bits (`mfc1`);
  - `0x10(sp)` = yaw, `0x14(sp)` = pitch, `0x18(sp)` = roll (`swc1`);
  - `0x1C(sp)` = handle.

  That is the o32 layout for that prototype, so the C prototype matches.
- **The ROM table `D_80089578`** (game_data) holds func_15110948, func_150FA030, func_150D1D20,
  func_15110B80 and func_15112074.
  - Registered signatures: `v:` (3 asm stubs), `i:iiii` for func_15110B80, and `v:` for func_15112074.
  - At runtime `unk8 = 0`, so func_15110948 (a stub) is called about once per frame. That call goes through
    `__port_icall_slow` (`fn is v:, called as i:iffffffi`).
  - The returned pointer stays valid: func_15110948 is in the `[DL]` list with 136 of 136 calls holding a DL
    pointer.
- **New `[icalltest]` cases** (`port/boot/game_icalltest.c`) call through a site of exactly this type:
  - an exact-typed C callee `Gfx *(Gfx *, f32 ×6, s32)`: all 8 arguments arrive and the returned pointer is
    used. **ok**;
  - a C callee typed `s32 (s32 ×8)`, through the slow path: a1..a6 are exactly the f32 bit patterns, a7 is the
    handle, and the return value is correct. **ok**. This is what a C func_15110B80 sees.
  - The test also prints `D_80089578[0..3]` with their registered signatures.
  - `port_fsig_of()` is new in `pc_icall.c`: a game TU cannot declare `__port_fsig` itself.
- **No bug.** One note for the port branch: the C `func_15110B80(Gfx *, s32, s32, s32)` gets x / y / z as float
  **bits** in arg1..3. It ignores them today. If they are ever used, type them `f32`.
