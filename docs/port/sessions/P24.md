**func_1000CEAC / func_1000D2F8 are not camera code.** They are the music sequencer's per-slot update (init_B1B0 =
audio: D_800417B0 players, osRecvMesg on D_80041E58[slot], func_10008xxx channel calls). The browser's guess that
they fill the projection buffers at D_800DC6D0 is wrong; whatever fills those is elsewhere. They are still per-frame
stub hits, so they are converted.

Notes owed to the browser's runtime check (UNVERIFIED):
- func_1000CEAC: the asm reads the beat length from a stack slot it never initialises (s0 from sp+0x8C) until the first
  beat message sets 0x514; in practice the value left by the previous slot's call. The C starts each call from 0x514
  (NM builds have no `.data` for a static). The difftest above used a test copy that reads the asm's slot.
- func_1000D2F8: the song callback (D_8002B074 record +8) is typed `s32 (*)(s32, u8, f32, f32, s32)` from the
  asm's register use (a2/a3 = the two floats, the 5th word on the stack); check the callee signatures on wasm.
  The callback path itself is not difftested: with random tables Unicorn mis-runs the `jalr` whose delay slot is a
  `swc1` (the known 2.0.1 FPU-delay-slot issue), so the setups above keep the record id small.
- func_1517FAD4: when D_800DE1BC == 0 the asm's colour lerp factor is an uninitialised stack float; the C uses 0
  (the wave path sets 0 too).
- func_1517E7FC: alpha starts as -1 (the asm starts from a stale stack word that only hidden nodes can see).

## Tools

- `DIFFTEST_RET="ADDR=V1;V2;..."`: successive calls return V1, V2, ... (the last repeats), e.g. a message loop
  `100238E0=0;0;0;0;1` (osRecvMesg, EU 0x100238E0). Single values work as before.
- difftest: a callee with a known prototype of <= 4 arguments has no outgoing stack args (hand asm such as
  func_150A8050 keeps ra at sp+0x10, which the contiguous-run heuristic took for an argument).
- `tools/port/difftest/nmasm_sincos.py` (container, from `/conker/conker`, after both builds): sin/cos/func_150A8050
  whole, through a trampoline that loads f12 from memory.
- **Harness fix (both nmasm harnesses):** the NM build's `.game_data` is not address-stable: absolute `D_` symbols
  such as D_8009FAB0 / D_8009FAE0 point into moved data in `build_nm/conker.eu.elf` (strings there). The candidate
  now runs on the reference's `.game_data` image. `nmasm_tri_box.py` re-run this way: 4000 trials, 0 differences
  (P22's run used the moved data for D_8009FAB0, the eps of the bounding-box slack).
- Unicorn caches translated blocks: a harness must not rewrite code at an address it already ran (one trampoline per target).
- EU addresses: symbols named after US addresses live elsewhere in EU (D_800417B0 = 0x80041B50, D_800DDD64 =
  0x800DE194, func_1000853C = 0x1000882C, ...). POKE/RET need the EU address: `grep '^NAME ' conker/symbol_addrs.eu.txt`
  or the `%lo` in the asm.
