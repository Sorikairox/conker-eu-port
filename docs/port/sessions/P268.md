# P268 (port-web, 2026-10-25): user crash "Em, this way I suppose" — memory corruption by a type-77 node handler

## 1. Reproduction
- Build 9e66f352 (the user's play build). Script `port_work/p268/run.sh DIR SECS BTNS PERIOD [QUERY]`: chR3 new-game
  start (Start 3386 / 4458), then button taps every PERIOD retraces from 4700 (no det, no autopilot).
- a1 (A every 150, no det) and a4 (A/B every 100, no det, ?p268nodes=1): **wasm "memory access out of bounds" at
  retrace 18970** (level 6, right after the level 0x1D cutscenes 4042 + 1083 frames). Crash site a1: func_151674F8 (node
  draw walk) from func_15018E88; the user's stack: func_151670C0 (node update loop) -> func_15168A2C -> B10 -> A9C.
  Both are the same thing: a broken link in the render-node lists D_800DD280[2][104].
- a2/a3/a6 (same scripts, no det) diverged (stayed in level 0x18 or no crash): the path is timing dependent, but when it
  reaches level 6 it crashed at 18970 both times. a5 was void (another Chrome run hid the tab).

## 2. Root cause (narrowed)
- NOTE: the user's stack frame `func_151670C0` is the **US-named update loop** (game_1944C0, EU 0x15167630), not
  `func_eu_151670C0` (spark_burst_tick, P263). The P263 lead does not apply: func_eu_151670C0's record layout matches the
  asm (sp+0x70.., 0x38 bytes copied by func_15167D84) and is not involved.
- Port diagnostic `?p268nodes=1` (port/gfx/p268_nodes.c): validates every list (index byte, group byte, prev link, heap
  tag) and re-runs the update loop with a check after every handler. Result (a4):
  `after handler frame 18970: list [0][28] node #4 10D19D10 ... list index` — **handler of type 77 (0x4D), group 1, on
  node 10D19980** overwrote word 0 of the next heap block's node (10D19D10 = 10D19980 + 0x390) with the float
  0x3F33B646 (0.70). The type-77 node's block is ~0x378 bytes, so something in its update writes a float at
  **node + 0x390, past the end of its allocation**.
- Type 77 update = func_15147CB0 (game_eu_1754C0, matched C) dispatching to the behaviour tables (EU, from the ELF
  with the .game_data offset +0xE0): D_8008A5A0[+0x2F] (15), D_8008A5DC[+0x30] (18), D_8008A624[s8 +0x24] (8), list in
  `port_work/p268/beh.txt`. Converted recently (registry): func_150D93CC (106830, P250), func_15199F80 (1C3530, P254),
  func_1519AF14 (1C3530, P231), func_151B69D0 / func_151B7DA4 (1E40E0, P255), func_151D1B80 (1FB080, P254),
  func_151D7EDC (204F70, P232), func_151D8280 (204F70, P238). One of the behaviours of that node writes an f32 at
  +0x390 of a node (likely a wrong struct cast: the record is used as a bigger object type, e.g. 0x390 = an object's
  yaw in game_14FF90 / 1501C0).
- Not finished: the run that logs the handled node's behaviour bytes (+0x2F / +0x30 / +0x24, added to p268_nodes.c)
  diverged twice and never reached level 6.
