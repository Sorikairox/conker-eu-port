## 1. The frame-19116 freeze (top priority): cause and fix

**Not a game-C bug. Port-side: `port/ultra/pc_pif.c` osContInit.** No bisect needed: the P233 log already pointed at
the EEPROM path, and the code confirms it.

- libultra's `osContInit` (conker/src_eu/init_eu_256E0.c:20, also game_eu_21D060.c func_151EF850) ends with
  `osCreateMesgQueue(&__osEepromTimerQ, &__osEepromTimerMsg, 1)` (EU D_80042E08 / D_80042E20).
- The port replaces osContInit with its own (pc_pif.c), which did **not** create that queue. It stayed zeroed
  (msgCount 0, msg NULL).
- osEepromLongWrite (game_eu_20ACB0.c func_151DD4A0) writes block by block: it arms a 12 ms timer whose message goes to
  D_80042E08, and the per-frame pump func_151DD588(0) (from game_eu_49310.c func_1501C55C) writes the next 8 bytes when
  that message arrives. With msgCount 0 the port's osSendMesg(NOBLOCK) dropped the timer message, so the long write
  never moved past its first block and `D_800E0E50` (pending queue) stayed set.
- The next save calls func_151DD4A0 again, which starts with `while (func_151DD588(1) != 0)`: an
  `osRecvMesg(&D_80042E08, NULL, OS_MESG_BLOCK)` on a queue nobody can fill. The game thread blocks for good, while
  audio and the page keep running: no trap, no retraces, null zone clean (exactly the P233 symptom).
- Why it showed up after 05b91168: P232 made **func_15006BEC save_slot_pack** C (game_33990.c, it was a stub
  before). Its first save is at the level-6 entry (frame 17824, P233 log: "1 block writes" = only the 0xFE block
  written directly by func_151DDA90; the 0x80-byte long write never progressed). The second save, at the level 0x18
  scene 2 request (frame 19116), blocked. func_15006BEC itself is correct; it just was the first C code to reach the
  game's long-write path.

**Fix** (port/ultra/pc_pif.c): osContInit now creates `D_80042E08` with `D_80042E20`, once (libultra does it once,
guarded by __osContinitialized). Not a TEMPORARY workaround: it is the missing libultra side effect.

Check: chR3 route, Chrome `port_work/p236/r29` (730 s): `[eep] saved ... 2 / 5 / 7 block writes` right after the level
6 entry (the long write now runs), frame 19116 and 19122 scene 2 requests (as P228), then level 0x18 scene 4 20184,
level 0x29 scene 1 22774, scene 2 26928, scene 3 30272, scene 4 32091, **scene 5 33659**, event 5002 started (act6 at
34211). Saves again at level 0x29 entry and around scenes 4 / 5 (10 .. 30 block writes in total). Traps 0, heap 0,

## 2. Race A: steering and laps

- **The ?p205goto autopilot followed the wrong record in Race A.** It reads D_800C3E78 in Conker's look callback; in
  Race A that names record 1 (the CPU racer). Run `race_go` "reached" all 30 waypoints only because the CPU drove
  them (positions identical to the CPU's in P233). New `?p205rec=N` (port/gfx/p205_obj.c): follow record N - 1.
- With `&p205rec=1` and waypoints at the rail-node centres (`race_go2.env`: (node + its type-4 edge node) / 2 for
  nodes 20..28, 0..19, 3 laps; GO_MAX 32 -> 100), run `race_go4`: the board did not get past waypoint 0 for ~4000
  retraces ("stuck" + jump/turn at 8201 .. 10301 around (4800, -9400) .. (6500, -6200)); from ~12100 it drove the
  track at CPU speed. The walking autopilot (learned stick-to-world offset, P205) does not suit the hoverboard; a
  proper steering controller (stick x from heading error) is the next step.
- **Lap counting works at record level.** New `?p236race=1` dump of the rail records D_80087640 (and the rail nodes
  D_800D2778 once): lap length 33 nodes, laps 3. In race_go4 the player's record went node count 4 -> 36 -> 68 and
  lap 0 -> 1 (13548) -> 2 (14556), as func_15088E84 computes (+0x27 = +0x24 / +0x26). The CPU finished first, so the
  STATS overlay was up (~13450) before lap 1 ended; the HUD "LAP 2/3" has not been seen in a shot yet. P233's
  "LAP 1/3 forever" was the player never finishing a lap (lava, respawns), not a lap-counter bug.
- `?p236rw=F` logs the player's rail tracking (func_150877C0 wrapped; port/Makefile `--wrap=func_150877C0`) on every
  update from retrace F for 600 retraces: position, t / node count before and after, nodes, side, normal. It showed
  the tracker follows the player when it moves; it stalls only while the player sits in lava (dies, respawns).
  rail_track_update runs once per 4 retraces per record in Race A (63 calls / 252 retraces).
- Rail node table (Race A, level 0x33): main loop nodes 0..28 with edge nodes 29..57, alternative branch 58..69
  (edges 70..81) from node 22 to node 3 (high road, y up to 1700), extra nodes 82 / 84 / 86 / 89
