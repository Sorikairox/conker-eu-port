# Session P6: safe indirect calls, F3DEX2 renderer bring-up, gfx task hook (branch `port-web`, 2026-10-22)

Everything is under `port/` and `docs/port/`. No game `.c` file, shared header or shared build file
was changed, so the matching N64 build is unaffected.

![ROM asset viewer](P6_screenshot.png)

## 1. Function-pointer call safety: done

Chosen approach: **site-typed trampolines with a runtime signature check.** The design and the
reasons are in `docs/port/MEMORY.md`, "Indirect calls (session P6)".

- **IR pass** (`port/tools/icall.py`, run from `vbe.py`):
  - 209 indirect call sites become calls to `@__icall.<hash>(fp, args…)`, emitted `linkonce_odr`;
  - each TU registers every function it defines (`static` ones included) together with its wasm
    signature id, from a constructor;
  - a `.isig` sidecar lists the TU's signatures.
- **`port/tools/icall_gen.py`** generates `port/stubs/icall_tab.c`:
  - it registers 1516 functions from the non-vbe objects (asm stubs, n64mem stubs, PC layer),
    using exact prototypes declared through asm labels;
  - `__port_icall_slow` has one case per target signature (218);
  - `port_fsig_name`;
  - `port_icall_check()`, the ROM-table registry test.
- **Runtime** (`port/ultra/pc_icall.{c,h}`): a 64K-entry `port_fsig[]` indexed by table slot, the
  register-file conversion helpers, and a log of the first 16 mismatches.
  `port_icall_report()` is part of the thread dump.
- **Totals after boot:** 5270 functions registered; 0 beyond the table cap; 0 registered twice
  with different signatures.
- **Tests (node and headless Chrome):**
  - `[icall] registry check over 5 ROM function tables: 654/654 entries OK`;
  - `[icalltest] PASS`: 8 calls of real `D_8008FC10` handlers through mismatching pointer types
    (f32↔int bits, missing or extra arguments, void→0, f32→f64).
- **Regression:** the 10 s boot is unchanged (543 frames, same stub ranking). In this run the game
  makes no mismatched indirect calls of its own, because the code that would make them is still asm.

Side fixes:

- `gen_stubs.py` no longer stubs JS-library imports (`gl*`, `emscripten_*`, `__port_*`) or the
  mirror arrays (`n64_*`). Its weak `void glClear(int)`-style stubs would have shadowed the WebGL
  imports.
- The scheduler demo had not linked since P4 (pc_mem's tables were undefined). It links again via
  `port/sched_demo/demo_stubs.c`.

## 2. Microcode findings

The ROM ships eight RSP gfx microcodes. They are uncompressed, between the init segment and the
game rzip. Their ucode-data strings are at ROM 0x3DDA8 + k·0x6C0:

```
RSP Gfx ucode F3DEX.NoN   fifo 2.08  Yoshitaka Yasumoto 1999 Nintendo.
RSP Gfx ucode F3DEX       fifo 2.08  …
RSP Gfx ucode F3DEXBS(.NoN)  F3DEXBG(.NoN)  F3DEXBGBS(.NoN)   fifo 2.08
```

- **Version and data size.** Version 2.08 is the F3DEX2 generation. The game builds with
  `F3DEX_GBI_2`, and display lists use the F3DEX2 encodings (`G_VTX 0x01 n<<12 (v0+n)<<1`,
  `G_MTX 0xDA380003/7`, `G_MOVEMEM 0xDC080008` viewport). The data block is **0x6C0 bytes per
  ucode**, against 0x420 for stock F3DEX2, so the DMEM tables are extended. "BS" and "BG" are Rare
  variants; what they change is not identified yet. The working guess is BG = background and
  BS = bone/skinning.
- **Ucode switching.** The per-frame builder `func_1501878C` (asm) emits `G_LOAD_UCODE`
  (`0xDD0007FF`, data size 0x800, text from `D_800BEFBC` via RDPHALF_1, data `D_800C1480`). The
  interpreter logs these and treats every variant as F3DEX2.
- **Opcodes the asm DL builders emit.** A scan of `lui`/`sw 0(base)` pairs found only standard
  F3DEX2/RDP opcodes: 01–07, D7–DF, E1–E4, E6–E9, ED–FF.
- **Non-standard commands, found in the model assets in ROM:**
  - **0x10–0x1F `TRI4` (Rare):** four triangles in one 64-bit command, as 12 five-bit vertex
    indices: `w0>>23`, `w0>>18`, `(w0>>15&7)<<2 | w1>>30`; `w0>>10`, `w0>>5`, `w0`; `w1>>25`,
    `w1>>20`, `w1>>15`; `w1>>10`, `w1>>5`, `w1`. Vertex loads of up to 32 vertices pair with them.
    The decoding is confirmed visually: asset 0x122C7A0 renders as a coherent mesh (top-left in the
    screenshot).
  - **`G_MOVEMEM` index 0x0E** (`dc38000e 00000410`) is **not** `G_MV_MATRIX`. It is followed
    immediately by the `G_VTX` it applies to and points at a small per-vertex array, so it is the
    vertex normal array. Conker vertices keep their RGBA as a colour even with `G_LIGHTING`. The
    interpreter records the base and does not apply lighting yet.
  - **`G_SETTIMG` texture ids:** w1 = `0x00000ED0` is the TLUT and `0x00400ED0` the texels of
    texture 0xED0. The engine must patch or resolve these before submission; no RSP can resolve
    them. Texture banks are also reached through segments 2/4–11.
  - **Segments:** in model files, segment 0/1 is the file itself (vertices, sub-DLs), segment 3
    holds bone matrices (`G_MTX` load from `0x03000080`…), and segment 8 is an engine material DL.

## 3. Renderer: `port/gfx/` (written for this port; see `port/gfx/LICENSES.md`)

- **`gfx_f3dex2.c`** is about 750 lines.
  - **CPU part** (Fast3D style): matrices with push/pop, projection and modelview, s15.16 `Mtx`
    from game memory; vertex transform to clip space; CPU back/front culling; `G_TEXTURE` scale and
    shift; fog factor; `G_MODIFYVTX`; `G_BRANCH_Z` (always takes the near branch); `G_DL`/branch
    with a 32-deep stack; `G_MOVEWORD` segments and fog; `G_MOVEMEM` viewport; TRI1/TRI2/QUAD and
    Conker TRI4.
  - **RDP part:** a byte-exact 4 KB TMEM, with LOADBLOCK and its dxt odd-line swaps, LOADTILE,
    LOADTLUT, and the odd-row xor on read. Formats: RGBA16/32, CI4/8 with an RGBA16 or IA16 TLUT,
    IA4/8/16, I4/8. Decoded tiles are cached on (TMEM generation, tile).
  - **Combiner:** one WebGL2 shader evaluates the generic two-cycle colour/alpha combiner from
    uniforms.
  - **Fixed-function state:** alpha compare (threshold, cvg×alpha), z compare/update, decal
    polygon offset, FORCE_BL alpha blending, fog blend, FILL/COPY modes, `G_FILLRECT` (a z-buffer
    fill clears depth), and `G_TEXRECT` with RDPHALF_1/2.
  - Unknown opcodes are logged once each.
- **Memory:** everything is read from game memory with the P4 rules. DL, `Mtx` and `OSTask` words
  use plain 32-bit loads; `Vtx`/`Vp` fields use `vbe_ld16`; texels use `vbe_ld8`.
- **Addresses (`gfx_addr`):**
  - KSEG0 values go through `port_n64_to_wasm`;
  - values at or above 0x10000000 are wasm pointers;
  - for a segment that `gsSPSegment` has set, `segtab[seg] + off`;
  - otherwise below 8 MB is the RDRAM mirror, and 16 MB to 256 MB is a wasm pointer that game C
    code stored.

  **Known ambiguity:** wasm addresses 0x01xxxxxx–0x0Fxxxxxx look like segments 1–15. A game
  pointer at 0x01xxxxxx (the RDRAM mirror is at about 0x010A9F20) is misread once the game sets
  segment 1. The clean fix is `-sGLOBAL_BASE=256MB`, which puts every wasm address above the
  segment space; its cost is about 384 MB initial memory. Decide this before game frames are
  live.
- **Entry points:**
  - `gfx_run_task(OSTask*)`: `osSpTaskStartGo` (`pc_os.c`) routes every `M_GFXTASK` here; `data_ptr`
    is the DL. `pc_video.c` then skips its placeholder clear for that frame. This is the path game
    frames will take once the frame builders are C. Nothing else needs to change.
  - `gfx_run_dl()`: interprets one list directly.
  - `gfx_demo_*()`: the ROM asset viewer.
- **Task log:** `osSpTaskStartGo` logs the first 8 tasks (type, ucode, `data_ptr`, size).
  `port_sp_report()` in the thread dump prints counts by type. **In the current boot run no task
  arrives** (`[sp] tasks submitted: 0`). The scheduler thread `func_100049E0` (thread 20, the only
  caller of `osSpTaskLoad/StartGo`) is still an asm stub and returns immediately. The frame
  builders `func_1501878C` and `func_1501BBB8` are stubs too.

### Proof: real display lists from the ROM

The page option `?app=game&gfxdemo=1` turns on the ROM asset viewer (`port/gfx/gfx_demo.c`).

1. It loads six model files straight from the ROM. Each is an rzip file: a BE size, then raw
   DEFLATE. They were found by scanning the ROM's asset area: 3715 streams, of which 124 contain
   textured DLs.
2. It inflates each file into wasm memory in the vbe layout.
3. It frames each model with a measure pass over its vertices.
4. Each frame it builds its own GBI display list (viewport, projection and modelview `Mtx`, render
   state, segments 0/1/3/8, then `gsSPDisplayList` into the model) and runs it through the
   interpreter.

The screenshot shows (headless Chrome, SwiftShader WebGL2):

- 2029 commands, 925 triangles, 48 of them from TRI4;
- 59 draws and 57 texture uploads per frame.

The two bottom-right models are heads; the eyes are visible.

Limitations:

- Texture ids and texture-bank segments are not resolved. They show a placeholder pattern: a CI
  hue palette and a checker. All texture loads, TLUTs and decodes still go through the real
  LOADBLOCK/LOADTLUT/TMEM path.
- No lighting.
- Skinned parts (asset 0xBA0708) collapse, because every bone gets the same matrix.
- The 0xF94550 bounds suggest that its vertices are not in segment 1 the way this viewer assumes.

To reproduce:

```sh
port/web/run.sh build
port/web/shot.sh out.png 'app=game&gfxdemo=1' 8000 [dom.html]
GFXDEMO=1 node port/tools/node_run.js …   # interpreter only, no GL; prints the frame stats
```

`gfxdemo=ROMOFF:DLOFF,…` (hex) picks other assets.
