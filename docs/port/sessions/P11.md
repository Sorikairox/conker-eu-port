## 1. Runtime check of the converted C

### Scheduler `func_100049E0`: correct, no bug found

The C body was compared with the asm instruction by instruction:

- the 7-entry jump table (read from ROM 0x2C400: 0, 1, 2, 3, loop, loop, 6);
- the timer arguments;
- the `OSScTask` offsets (`list` at 0x18, `msgQ`/`msg` at 0x58/0x5C);
- the yield paths.

All of them match. The queue names differ (C `D_8003B218`/`D_8003B200` against asm
`D_8003B578`/`D_8003B560`), but these are US names that `undefined_syms.eu.txt` maps to the same EU
addresses. The port labels alias them (checked in `n64mem_labels.s`).

The scheduler stayed asleep for two reasons, both on the PC side:

- **The PC `func_10001194` (port/boot/game_main.c, P4) had left out the asm's cold-boot block**:
  `osCreateMesgQueue(&D_8003B218, 0x8003BC10, 8)`, `osViSetMode`, `osViBlack(1)` and
  `osViSetEvent(&D_8003B218, 0, 1)`. Without the VI event the scheduler never woke up. Fixed in
  `game_main.c`.
- **The heap bounds were KSEG0 constants.** `func_10003930` (C) stores 0x803F5000/0x803FE000 in
  `D_80038090..9C`. `func_10003BD0` then computes the heap size as `D_80038098 - &D_800EA140`, a
  K0 constant minus a wasm address. The size came out at about 1.9 GB, and the first top-down
  allocation, now that `func_10003C6C` is C, trapped out of bounds. The PC fix-up
  `port_fix_heap_bounds()` (game_main.c) rebases the four words into `n64_rdram`. This is the
  "address constants" gap from P4.md. The C is a faithful translation.

**Self-test `port/boot/sched_test.c`**, which runs in a thread at priority 12:

- It registers as a scheduler retrace client with the game's `func_100051C8`. It must register
  after `func_100050A0`, which clears the list. All 6 retrace messages arrive, each `&D_8003B240`
  holding 1.
- It sends a gfx task to the gfx queue `D_8003B1E8`. The path is `func_10004DB0` →
  `func_10004F00` → `gfx_run_task`, then the SP and DP events, then `func_10004FE0` →
  `func_10005020` → the done message. Result: the right message after 2 frames.
- It sends an audio task to `D_8003B200`. The path is timer message 3 → `osSpTaskStartGo` →
  `aud_run_alist`, then message 2 → the done message. Result: the right message after 2 frames.

So **RSP gfx and audio tasks reach `gfx_run_task` and the audio interpreter** through the C
scheduler.

The test also showed one rule: a gfx task must not be sent to `D_8003B200`. Its DP event makes
`func_10004FE0` complete a NULL `D_8002AC50`, and the run traps in `osSendMesg`. That is N64
behaviour (only audio tasks use that queue), not a bug in the C.

### Allocator `func_10003C6C`: correct, no bug found

`port_heap_check()` walks the block list and the free list after boot:

- 9 blocks, 2 on the free list, 0 errors;
- the blocks tile the heap, and the next/prev links agree;
- used 378712 bytes: two framebuffers and a z-buffer of 126144 bytes each, plus the test blocks;
- the test's allocations are 16-byte aligned and land inside `n64_rdram`.

The first block sits 0x34 bytes after `&D_800EA140`, because of the class-3 (64-byte) alignment.
This revealed that `n64_rdram` was only 16-byte aligned in wasm, so alignment arithmetic could
differ from the N64. **The mirrors are now aligned to 4 KB** (`n64mem.py`, `.p2align 12`), which
puts the first block at the N64 offset.

### Asset walker `func_1502AC88`: correct, no bug found

`port_asset_check()` compares the game's `func_1502B020(&ok, 2, a, b)` (C) → `func_1502AC88`
(C) with a direct PI-DMA walk, for 8 keys. All 8 match, `ok`/info included; for example (0x17,2)
gives 0x2A19E88 with info 0x14B3330. The MRU insert `func_1502AB04` is still asm, so every lookup
misses and does a DMA. That is correct, only slower: the top stub is 217 calls at init.

### NULL writes

The null zone holds 33 words (0x10..0xD0). They are display-list words that the frame builders
write through a NULL `GDL`, because the DL buffers are never allocated (§2). The scheduler,
allocator and asset walker write none of them.

## 2. Live frames: the frame is built, but no game DL is rendered yet

The path to a game frame has five steps:

1. **First pad read.** `func_1501BBB8` (C, P10) blocks on the SI queue `D_800BED20` before any
   read starts. Reads start from scheduler message 6, sent by the 25 ms timer that
   `func_1501BB20` arms. The level loader **`func_15007B3C` (asm stub) calls `func_1501BB20`**,
   so on the N64 that call starts the first read.
   - PC shim: the PC `osContInit` (pc_os.c) posts one SI message.
   - Remove the shim when `func_15007B3C` is C.
2. **`func_15019130`** (asm, the world update, about 90 callees). `func_1501878C` returns before
   building when it returns 0.
   - TEMPORARY PC override in `pc_overrides.c`, translated from the asm with delay slots
     resolved.
3. **DL pass-through stubs.** An asm function that the game only calls as `x = f(x, …)` now
   returns `a0` instead of 0 (`gen_stubs.py`, 23 stubs; the stub list marks them `:passthru`).
   The GDL then survives to `gDPFullSync` / `gSPEndDisplayList`.
4. **`func_eu_1501C860`** (asm) is the frame submit.
   - It fills `OSScTask D_800BEEF8[idx]` and sends it to the gfx queue (EU 0x8003B548).
   - TEMPORARY PC override. It uses the addresses that the asm's symbols resolve to:
     `undefined_syms.eu.txt` remaps US names, for example `D_800BE9C0` → 0x800BEDE0 and
     `D_800BE9D0` → 0x800BEDF0. An earlier draft that used the literal names as addresses read
     the wrong variables.
5. **The DL buffers `D_800BEDE8[2]` are NULL.** They come from `func_15015E30` (C since P10),
   whose only caller is `func_15007B3C`, the asm level loader (451 lines, about 90 calls).
   - The override therefore drops the frame. It posts the retrace message to the main queue, as
     `func_10004F00` would, so the game still steps every frame.
   - **No game gfx task is submitted, so there is no screenshot.**

**What the first DL contains** (written at NULL+0x10, since `GDL` = 0):

| words | meaning |
|---|---|
| `DE000000 8002CC90` | G_DL to the static setup DL at 0x8002CC90 |
| `FE000000 800EA180` | G_SETZIMG to the z-buffer, the first heap block |
| `DC080008 00000050` | G_MOVEMEM viewport from a NULL-based address (a stub returned 0) |

After that come the RSP setup (`gSPLoadUcodeEx`, geometry mode, `G_MOVEMEM` lights) and
FullSync/EndDL. The DL ends at 0x38 for the empty world.
