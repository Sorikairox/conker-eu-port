### Root cause of the Chrome trap (diagnostic wraps, `?p131mdl=FRAME`)

1. func_1510D3E0 walks a "display list" at 0xE76D8652 (outside memory). It is asset (9, 189) loaded through the
   multi-list loader func_15030100, but asset 189 is a one-list model (hdr[1] = 0x90, hdr[0] points at a DL
   `D7000002 FFFFFFFF`), so `table[0] + hdr` is garbage.
2. Index 189 comes from setup command list **178** (func_15083568 enter log), which is past the end of the
   D_80087064 table (ROM game_data dump: list 178's "commands" are floats / pointers / strings). Node got list 18 for
   the same object.
3. The list number is `e[0x29]` of the level-setup entry passed by func_15022440. The setup asset (2, 0xE, 0x18) is
   loaded correctly (`[p131] setup asset (2, E, 18) frame 4583 -> dst 1066CC40 size 3C0`: entry 5 = `00200102 0C00FF02 ...`,
   table base 1066CB50), but func_15082E44 receives entry 5 at **1066DA50 = base + 5 * 0x300** (bytes there are texture
   pixels `xxxxxxFE`, different per run - which explains node vs Chrome).
4. **Bug**: `conker/src_eu/game_eu_4A070.c:2447` (func_15022440, NON_MATCHING, P16 batch body):
   `func_15082E44((sp38 * 0x30) + D_800D20FC, ...)` with `extern struct258 *D_800D20FC` (sizeof 0x10) scales the
   index by 0x300. The asm (`sll a1,2; subu; sll 4` = a1 * 0x30, added to the loaded pointer) uses bytes. Fix:
   `func_15082E44((u8 *) D_800D20FC + sp38 * 0x30, ...)`. m2c_sanity did not flag it (struct pointer, not an
   i32 / u8 table). Not fixed here (game C outside merge resolution).
