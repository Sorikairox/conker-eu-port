# P21 (branch `port-web`): browser-only heap corruption fixed (fiber stack alignment); real-time Chrome runs

Started at cfcee70 (P19). Everything is under `port/`; no game `.c` changed.

## 1. The browser-only heap corruption (P19 §6): FIXED

**Cause: the fiber C stacks were only 8-byte aligned.** `osCreateThread` (`pc_sched.c`) took each fiber's
C stack from `malloc`, which guarantees 8 bytes. wasm code assumes a 16-byte aligned `__stack_pointer`:
clang gives local arrays 16-byte alignment and then folds the game's own `((u32)raw + 15) & ~15` to
`raw`. Whether a stack happened to be 16-aligned depended on the mallocs done before it. The browser
does a few (WebGL context creation); node does none.

How it broke the game:
- With an 8-mod-16 stack, `func_1502AC88` (asset-table walk, `rec = buf + (key & 0xF)`) read its ROM
  record 8 bytes off.
- The audio init `func_10008180` then loaded the wrong asset, and the level loader allocated with
  garbage sizes. The heap was corrupt at the first `func_1502B350`, and `func_10003C6C` trapped.

How it was found:
1. Make the run deterministic (`det=1`, below).
2. Compare node and Chrome. `nogl=1` in Chrome gave node's behaviour, and `mallocpad=16` in node
   reproduced the browser crash.
3. Diff the logged PI DMAs (`dmalog`/`dmamin`) of the two layouts. The DMA of ROM 0xAB22F0 landed at
   0x14EB0530 in one run and 0x14EB0548 in the other, so the "16-aligned" buffer was not aligned. The
   next DMA read ROM 0x013313C0 instead of 0x029AF930.

**Fix:** `aligned_alloc(16, …)` for the fiber C and asyncify stacks, and `aligned(16)` on the scheduler's
asyncify stack. After the fix, node gives the same result with `mallocpad` 0, 8 and 16: the first asset
is ROM 13306F8, the heap has 0 errors and frames run. Real-time Chrome has 0 heap errors, and frames
keep coming past frame 480.

**Rule: any memory used as a C stack must be 16-byte aligned.**

None of the other suspects was the cause:
- thread timing;
- ASYNCIFY stack overflow (the overflow traps);
- the 352 MB layout;
- Web Audio re-entrancy (the callback makes no wasm call).

## 2. Real-time freeze: page responsive

- **Metal ANGLE (real GPU, `PROBE_ANGLE=metal`), 35 s:**
  - more than 480 gfx frames;
  - `Runtime.evaluate` answered at 15 s ("Conker Port 226");
  - no slow frames.
- **SwiftShader (default), 15 s, with `PROBE_EVAL_TIMEOUT=30000`:**
  - every evaluate answered; the slowest took 3.4–4.1 s, during startup;
  - about 40 VI frames per second;
  - no thread hit the spin limit; no frame ended on the time budget.
- **What the earlier "does not respond" reports were:** the 4 s evaluate timeout of `audprobe.js`
  firing during startup.
  - On SwiftShader, `getContext` alone takes about 1.7 s (CPU profile, `PROBE_PROFILE`).
  - Debugger pause samples are unreliable here. The first sample always lands at the same place, an
    asyncify rewind through `__port_icall_slow` ← `func_151E8620`, and later samples land at
    `MainLoop_runner`. A likely cause is V8 tiering the 3 MB module down for debugging first; this is
    not confirmed.
- **Hardening in `pc_sched.c`:**
  - **Spin park:** a thread that reaches the spin limit in `port_spin_check` is parked until the next
    frame, so `pick()` skips it. Before this, it was picked again at once and burned the whole frame.
  - **Time budget:** `port_sched_run` returns to the browser after 40 ms of wall time. This is
    skipped under `det=1`.
  - **Slow frames:** frames slower than 250 ms are logged with the switch counts per thread.
  - **Dump:** `port_dump_threads` reports frames, budget-ended frames, slow frames and the spins per
    thread.
- **Node, 10 s:** 534 frames, 133 gfx tasks and 266 audio tasks. One frame ended on the budget (the
  loader); there were no spins.

## 5. New debug tools

### Runtime flags

The page reads `?name=N`; node reads `PORT_NAME=N`. `boot.sh` passes every `PORT_*` variable to node.

| flag | effect |
|---|---|
| `det=1` | Deterministic clock: frame × 1/60 s plus 1000 ticks per read; no wall-time budget. Node and Chrome runs can be compared. |
| `nogl=1` | No WebGL context (node-like). |
| `noselftest=1` | Does not start the P11 scheduler self-test thread. |
| `heapwatch=1` | Walks the game heap after every scheduler switch and on every `osSetIntMask`. The first broken walk is logged with the thread, the frame, the last clean point and a JS stack. Heavy in Chrome: the loading frames slow to about 1 per second. Clean in node and in Chrome with this fix. |
| `stubstack=1` | Wasm call stack of each first stub hit. |
| `dmalog=N` and `dmamin=DEV` | Logs the first N PI DMAs from ROM offset DEV up, with the first two words. |
| `mallocpad=N` | `malloc(N)` before boot, to shift the malloc layout. This is the test for layout-dependent bugs. |

### `audprobe.js` environment variables

| variable | effect |
|---|---|
| `PROBE_LOG=file` | Streams the page console as it happens, so a hung page still leaves its log. |
| `PROBE_GREP` and `PROBE_TAIL` | Select which console lines are printed at the end. |
| `PROBE_EVAL_TIMEOUT` | Evaluate timeout in ms. The run ends with "evaluate: slowest answer N ms". |
| `PROBE_SAMPLES` and `PROBE_DEPTH` | Number of pause samples taken when the page hangs, and the stack depth printed. |
| `PROBE_PROFILE=ms` | CPU profile of the first ms, as top self time per function. |
| `PROBE_ANGLE` | ANGLE backend (default SwiftShader; `metal` uses the GPU). |

C helpers: `port_flag(name)` and `port_js_stack(skip, n)` (`pc_os.c`).

## 6. Facts for the port branch

- `D_80090370[D_800E0B94]` in `func_151E8620` calls the asm stub `func_151EC11C` (table #4958). It is
  `v:` called as `i:i`, so it returns 0 and `func_151E8620` returns a NULL `Gfx*` every frame. Node does
  the same. Converting `func_151EC11C` (and the other entries of `D_80090370`) as `Gfx *f(Gfx *)` is
  needed before the frame DL goes past the viewport.
- `__osRunningThread` is never set by the PC scheduler (it is 0). `func_10004514` reads
  `__osRunningThread->id` from the null zone, so its thread-3 fast path (`func_1000480C`, an asm stub)
  is never taken. This is harmless now.
