## 1. func_15001A08: PI_STATUS and the cart word

The raw IR (`port/build/ll/game_eu_2F180.c.ll`):

```
%7  = load volatile i32, ptr inttoptr (i32 -1537212400 to ptr)      ; PI_STATUS 0xA4600010: already rcp_io (P19)
%12 = load i32, ptr @D_80000308                                     ; osRomBase
%13 = or i32 %12, -1342173916                                       ; | 0xB0000D24
%14 = or i32 %13, -1610612736                                       ; PHYS_TO_K1: | 0xA0000000
%15 = inttoptr i32 %14 to ptr
%16 = load volatile i32, ptr %15                                    ; -> trap
```

- **`vbe.py rcp_io`:** a volatile i32 load through `inttoptr` of an `or x, 0xA0000000` becomes
  `call i32 @__port_io_read(i32 x)`.
  - 4 sites are rewritten in the build: func_15001A08, plus the weak libultra `osPiRawReadIo` (the PC version overrides
    it), `__osSpRawReadIo` and `osSpTaskLoad` (neither is run).
  - Before this change, those would have been wasm loads at 0xA4.../0xB0... too.
- **`pc_os.c __port_io_read`:** for `(a & 0xF0000000) == 0xB0000000` it returns `osPiRawReadIo(a)`, the big-endian
  ROM word at `a & 0x0FFFFFFC`. It logs the first 4 reads.
- Result: `[io] cart read 0xB0000D24 = 0x98CCE31A` at both level loads. That is the value the asm compares against
  (`0x98CCE31A`, also read from the ROM in Python), so the node pool keeps its table size (`D_80091EA0[level]`) and is
  not doubled.

## 3. The real visibility walk (`?vislog=N`)

`vislog` now logs the first N calls of **every (dl, tree) pair**, so the level after the boot level is covered too. At
the first call of each pair it adds:

- the leaf-list sizes;
- the game's pool counters D_800B0DCC / D_800B0DD0 (EU 0x800B11DC / 0x800B11E0, all areas);
- the first two vertices of the source DL;
- the D_800D9FB0 records.

With `vislog=3` and up, it also dumps the emitted commands.

Node, 40 s:

```

[vis] tree 106445F8: 53 nodes, 40 leaves, 0 leaves start with a relative index (first 00000000); leaf entries 167 (max 8 per leaf); pool counters (all areas) nodes 55 leaves 41
[vis] new dl/tree 1063DD80 / 10645518 after 179 calls
[vis] call 0 dl 1063DD80 mask 1: src 104 cmds 288 tri slots; out 73 cmds 172 tri slots; vis bytes 168/288
[vis] tree 10645518: 101 nodes, 76 leaves, 0 leaves start with a relative index (first 00000000); leaf entries 388 (max 97 per leaf); pool counters (all areas) nodes 103 leaves 77
```

- **Triangle count:**
  - `dlapprox` draws the whole D_800B0E00[0], 288 slots. The real walk emits 172, the same in every frame, because
    the game view is fixed.
  - The 168 visibility bytes for 172 slots: a Rare TRI4 can hold degenerate slots.
- **Tree:**
  - The pool counters (103 nodes, 77 leaves) equal P40's harness numbers for the C-built level 0x21 tree.
  - The vislog scan reaches 101 / 76 through the child (+0xC) and sibling (+4) links; the pool also holds the area
    headers.
- **Output:** normal level DL. Render state, tile loads, `01020040 1063CD00` (VTX) and TRI4s. No garbage commands
  and no unknown opcodes in 30 s. That closes P34's other UNVERIFIED item: real level data shows geometry.
- **P34 $gp:** 0 leaves start with a relative byte on either level, so "previous index = 0" (C) versus "the caller's
  $gp" (asm) makes no difference. **Closed.**

## 4. Why the level is black without `?lvlwhite=1` (stub-dependent, not a C bug)

`?drawlog=500` shows the level vertices lit to rgb 0 (`lights BG set nls 48 ambient 000000`). The vertex colours in
memory are FFFFFFFF.

- Before the level, the C func_1515DE84 (P32) emits `G_MW_NUMLIGHT = 0x30` (count 0 + 1), a movemem of the ambient
  record to record 0 (black, because `flags = 0x25` has no bit 2), and `arg8` to record 1.
- BG (P35b) starts the accumulator at record M = 1 = `arg8`. `arg8` is a copy of the local `col[4]`, which the
  **still-asm func_1515E7E8** (game_eu_18B1C0, 532 calls in 30 s) should fill.
- With the stub, `col` is uninitialised stack. In P39 it happened to be dim green, which is the green tint in
  P39_screenshot. In this build it is 0, so the level is black.
- **For the port branch:** convert func_1515E7E8 (and func_1515E9AC, for `flags & 2`). Until then the level colour
  depends on stack contents.
- **`?lvlwhite=1` (diagnostic, `gfx_f3dex2.c light_vtx`):** for the BG ucode, a start colour of exactly 000000 becomes
  white.
