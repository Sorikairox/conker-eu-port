# P269 (port-web, 2026-10-25): the "Em, this way I suppose" crash — func_151D7FE8 vel pointer stride bug

## 1. Reproduction (deterministic)
- `docs/port/sessions/p269/run.sh DIR 300 8000,4000 100 "&p268nodes=2&det=1&timer=2"` (the P268 tap pattern: A/B
  every 100 retraces from 4700, chR3 new-game start). With det=1&timer=2 the run reaches level 6 at 17885 and traps
  "memory access out of bounds" at **retrace 18969** every time (f2, f3; ~2.5 min wall time). Levels: 25 -> 21 (725)
  -> 1D (2165) -> 18 (4565) -> 1D (10805) -> 6 (17885), the same frames as the user-like P268 a4 run.
- det=2 works too but is far slower with the old full `?p268nodes=1` checker (it scans all lists after every handler).
  New cheap mode `?p268nodes=2` (port/gfx/p268_nodes.c): only type-77 nodes, logs each kind once (size, +1E, +24,
  +2F, +30) and any write to the 8 words after the node's heap block, per behaviour (link wraps of func_151D7EDC /
  func_151D7FE8 / func_151D8280).

## 2. Culprit
- The type-77 node is the trail object of func_151D7DE0 (game_eu_204F70): ring of +0x25 = 25 entries of 0x1C bytes at
  +0xC0 (+0x94), data block 0x37C. Behaviours +2F 13 = func_151D7EDC, +30 16 = func_151D7FE8, +24 4 = func_151D8280.
- `[p269] func_151D7FE8 wrote past node 10D1BA70 (size 37C): +390 10D192C8 -> 3F33B646 | before +2C 1 +2D 23 +2E 24`
  (f3_overrun.txt): adding a point at ring entry 24 (the last one) writes the next heap block's node link.
- Cause: P17 batch m2c body. `temp_a0` is `f32 *`, and the call is
  `func_151D8CC8(temp_a0, temp_a0 + 0xC, var_f22);` -> the velocity pointer is entry + **0x30** bytes (f32 stride),
  the asm has `addiu $a1, $a0, 0xC` (entry + 0xC). func_151D8CC8 then stores the velocity (f32 0.70) 0x24 bytes too
  far: for entry 24 that is node + 0x390 = the `next` link of the following node in D_800DD280 -> broken list ->
  wasm trap in the node draw/update walk. For entries 0..23 it silently clobbers the next entry's +0x18/+0x1C.

## 3. Fix (owner: **port**, game_eu_204F70 is not in port-b's list)
```
-            func_151D8CC8(temp_a0, temp_a0 + 0xC, var_f22);
+            func_151D8CC8(temp_a0, (f32 *) ((u8 *) temp_a0 + 0xC), var_f22);
```
(conker/src_eu/game_eu_204F70.c, func_151D7FE8; patch: p269/fix_151D7FE8.patch.)
- difftest (function alone, 200 trials): old C **DIFFER** `call #0 0x151D8CC8: a1 ref=0x805D8E44 cand=0x805D8E68`
  (+0x24); fixed C **EQUIV** (114 ok, 49 via learned pointers). No registry row yet (never verified before);
  port should add one with the fix.
- Browser test with the fix as a TEMPORARY local edit (vbe.stamp deleted, rebuilt): f4 ran past 18969 to retrace
  40325 (level 6 -> 18 at 19205 -> 29 at 22805), **0 traps**, no writes past type-77 blocks. The edit was reverted
  before the commit (vbe.stamp deleted again: rebuild before the next browser run).
- Side note: one logged "OVERRUN" at 17961 is the next block's heap header tag 01000784 -> 03000784, i.e. the
  allocator itself (a node freed/allocated during the handler), not a stray store.

## 4. Same bug class elsewhere (leads, unverified; p269/stride_leads.txt)
Typed `s16 *` vertex pointers advanced with `+ 0x10` (C: 0x20 bytes; asm: `addiu 0x10`): func_150D4810
(101080, port-b), func_151C3080 (1EFE10, port), func_1519CADC (1C3530, port-b), func_151CE3D0 (1FB080, port-b).
These would write vertices at double stride (past their vertex buffers). The difftest of func_150D4810 failed to
build (CERR: missing externs D_800914B0 / D_800D30BC in the candidate), so they are not confirmed.
port/tools/m2c_sanity.py should get this pattern (typed pointer + hex byte offset, not via `(u8 *)`).
