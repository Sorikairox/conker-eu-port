# Session P94: why Conker's hoodie is green in the respawn cutscene (branch `port-web`, 2026-10-23)

Worktree `~/conker-wt/web`, container conkerdev-web, image conker-emsdk. Investigation session. Only renderer code was
changed (`port/gfx/gfx_f3dex2.c`); no game C was edited. verify_all OK (rc 0).

## Verdict

**It was a renderer bug, not cutscene lighting.** There were two bugs in the character lighting, and both are fixed:

1. **G_LOAD_UCODE operands swapped.** In gSPLoadUcodeEx, `G_RDPHALF_1` carries the ucode **data** and the
   `G_LOAD_UCODE` w1 carries the **text**. The port read them the other way round, so after every G_LOAD_UCODE (the
   character ucode) it seeded DMEM (light records, Rare 0x10 block, normals) from the RSP **code**.
   - Record 2 (DMEM 0x320) then held the instructions `4B6B58F2 4B6A58B1`, and the old model read them as the
     ambient colour **4B6B58** (green-grey).
   - With the fix, `[ucode] loaded data` names `F3DEX.NoN fifo 2.08`; before, it found no name. The ucode
     text/data comparison and the log line were swapped too, and are fixed.
2. **Wrong light model for the character ucode.** P35 had marked this model "unchecked". P35 read record M as a
   directional "sun" and record M+1 as the ambient. P94 disassembled the F3DEX.NoN lighting overlay
   (`p94/f3dex_light.dis`, IMEM 0x12D8.., same place as P35's F3DEXBG overlay; 339 of 0x1400 text bytes differ,
   starting at 0x1294). It shows a different model:
   - 0x13F8 `luv $v29, 0x170($9)`: the start colour is **record M** (the ambient), as in BG.
   - 0x1418..0x1468 `lpv 0x158($9)` / `luv 0x140($9)` / `vmulu`+`vmacu` / `vmacf`: **record M-1 is directional**:
     `c += col[M-1] * max(0, n.d)`.
   - 0x1474..0x1590: records M-2..0 are point lights, two per pass, with the K byte at +0x0C and the n.d factor
     when geom has 0x400000. 0x1594..: `rgb = vertex rgb * min(1, c)`; a vertex flag high byte < 0 keeps its colour.
   - The game's DL agrees. func_1515EAB4 (NM C, P82 lineage, not a stub) sends `NUMLIGHT 0x30` (M = 1), then
     record 0 = `FEFEFE00 FEFEFE00 1D4DA000` (a white directional light, K = 0) and record 1 = `7380B100` x4
     (gSPSetLights1's Ambient; the 48-byte DMA brings trailing RAM pointers with it).
   - So P35's model used the ambient as a "sun" whose direction was its own colour bytes (115, -128, -79). It dropped
     the white key light (K = 0, so attenuation 0) and took the start colour from record 2, which nothing writes.
   - The result changed with the model's orientation relative to that garbage direction. That is why the hoodie was
     blue in some frames (P88 at 50 s) and green, with yellow gloves, in others (P91 respawn scene at 41 s).

The light values the game sends are the same in the cutscene and in normal play, and they look sane:
- `?p78tex` with the new `[p94light]` lines at node task 360 (scene) and task 520 (after the scene).
- In both: record 0 = FEFEFE with direction (22, 91, -84) / (29, 77, -96), record 1 = 7380B1, NUMLIGHT 48.
- func_151462C8 (P82 C) and func_1515EAB4 are C, and neither is on the stub list.
- The game side looks right. **No game C fix is needed.**

## Second question: the green quad (respawn approach, about 33 s)

- Chrome `?p78tex=480`: the task matches the scene table view (944 commands / 635 triangles). The dump limit is now
  256 rows for strips up to 8 texels wide.
- The quad is G_VTX 4 at x/y ±1750, z -1000, t 292.06 (top) .. 667.06 (bottom), geom 200005 (unlit).
  - Material: tile 0 RGBA32 4x256, ul 256, lr 259/511, cms/cmt clamp, mask 2/8.
- **The texture itself is a sky-to-ground gradient** (`p94/sky_gradient_rows.txt`). It is piecewise linear:
  - rows 0..167: blue 0000BF to white D0D5FF;
  - rows 167..177: down to dark green 124E19;
  - rows 177..222: dark green to bright green 00C700;
  - rows 222..255: flat 00C700.
- The segments are smooth, so the texels are not corrupt, and the RGBA32 TMEM decode is consistent.
- The RDP clamps t to the tile's lrt (row 255) when cmt has the clamp bit. So `t - ult` = 36..411 shows the gradient
  for the top ~58 % and the flat green row 255 below it.
- **The flat green therefore matches N64 semantics for the s/t the game sends.** The green is the gradient's
  "ground" part.
- Still open: whether the game's t range (292..667) is right. It comes from the game's sky code and was not traced.
  The black region above the green in `p94/sky_greenquad_33000ms.png` was not identified either.

## Changes (`port/gfx/gfx_f3dex2.c`)

- G_LOAD_UCODE: text = w1, data = RDPHALF_1. `dmem_seed(rdphalf1, ...)`. `?p94oldseed=1` brings back the old seed.
- `light_vtx`, non-BG: start = record M, directional = record M-1, point lights M-2..0. `?p94oldlight=1` brings back
  P35's model. The BG path is unchanged.
- `?p78tex` also logs `[p94light]`: every light-state change (records, model-space directions, geom, combiner,
  prim/env/fog) and its first 2 lit vertices (normal, c, rgb in/out).
- `?udump=2`: hex dump of the loaded ucode, text 0x1800 + data 0x800. `p94/rspdis.py BIN START END IMEM` disassembles
  it (rabbitizer RSP, in conkerdev-web).
