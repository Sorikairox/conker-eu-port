## 2. Gravity and the frame time

New: `?p49walk` also wraps **func_1505A770** (the walk handler's call) and logs `[p52] gravity` lines:

```
[p52] gravity call 1 frame 723: dt D_800D1550[0] 1.2 (bits 3F99999A) grav 6 | y 1 -> -3.32 yv 0 -> -7.2 +28 0 -> 0 | +180 1 floor118 -10000
[p52] gravity call 2 frame 725: dt D_800D1550[0] 2.4 (bits 4019999A) grav 6 | y -1 -> -26.92 yv -7.2 -> -21.6 ...
[p52] gravity call 48 frame 909: dt ... 2.4 ... | y -1 -> -618.28 yv -500 -> -500 ...
```

- Ground branch (+0x28 == 0, vy <= 0): `vy -= g * dt`, `y += vy * dt * 0.5` with the unclamped vy, then the clamp:
  -7.2 x 1.2 x 0.5 = -4.32 (1 → -3.32); -21.6 x 2.4 x 0.5 = -25.92; at the clamp -514.4 x 1.2 = -617.28. All match
  the C and P50's description.
- **D_800D1550 trap (P50):** the symbol is the f32 itself; the C reads `*D_800D1550` = 1.2 then 2.4. Sane (2.4 = two
  PAL fields in 1/60 s units).
- **Why y does not decrease:** after gravity the handler queries the floor (game_eu_78230.c:2416-2463:
  func_150A44A4, a stub that returns 0, then func_1510EE3C → stub func_1510EED0). The floor height output `spC4` is
  never written; it reads 0 (stack contents: undefined, it could be anything). Then line 2569:
  `if (y < spC4 + spC0 && vy < 0 && ...) y = spC4 - 1` → y = -1 every call, and +0x180 = spC4 = 0. vy stays at -500
  because the landing code func_1505A9AC (stub) never resets it. P49 had y = 1 because vy stayed 0 (stub gravity).
- **Diagnostic `?p52void=1`** (`port/gfx/p49_walk.c`, wrap of func_1510EE3C): writes -10000 ("no floor", what the
  real query returns off the level) to spC4 and +0x118. The player then falls under the C gravity:

```
y: -3.32, -29.24, -72.44, -132.92, ... -547.64 (call 8), ... -8842.04 (call 32), then -10001 (snapped to spC4 - 1)
```

  The camera keeps `at.y = 1` and eye.y = 400 while the player falls, then moves the eye to -9600 (= -10000 + 400)
  once y is snapped to -10001. So with the real floor query the player will fall off the edge; to check after
  func_1510EED0 is C.

## 4. The black screen

`PORT_DLSTAT=8 PORT_VISLOG=2000 PADSCRIPT="15000:0:0:80"` (stick held from 15 s; `boot_p52_vis.log`,
`boot_p52_hold.log`):

```
[vis] ... dl 1063EDB0: src 288 tri slots; out 288 tri slots; vis bytes 288/288    (43 calls, standing / starting)
[vis] ... out 252 ... 238/288;  out 172 ... 168/288;  out 114 ... 97/288
[vis] ... out 0 tri slots; vis bytes 0/288                                       (all later calls)
[gfx] frame 224: 338 commands, 288 triangles   (player at about (-279, 436))
[gfx] frame 240: 290 commands, 114 triangles
[gfx] frame 248: 236 commands, 0 triangles     (player at about (-730, 1043))
```

- No NaN anywhere in the log; eye / at stay finite (`at` = player, eye about 750 behind at height 400).
- At gfx frame 248 the eye is about (-283, 400, 440) looking toward the player at (-730, 1, 1043): the view direction
  points away from the origin, and the floor (around the start, where the player spawned at (27, 1, 27)) is behind
  and below the camera. The visibility walk's per-leaf tests drop the floor leaves one by one (288 → 0); the renderer
  gets no triangles. This is the right result for that camera.
- Cause: no floor or wall collision (func_1510EED0, func_150A44A4, func_15044950, func_150AB6D0 / func_150AC8C4 are
  asm), so the player walks off the floor at 600 units/s, and y is held at -1 by the stub floor height (§2).
- The Chrome frame sequence shows it: `walk_00` floor, `walk_02` the floor's far edge, `walk_03` a sliver at the
  bottom, `walk_04` and after black.
