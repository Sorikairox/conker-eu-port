# P33 (branch `port-web`): the level-load heap break, real level geometry on screen

Started at ef9107d (P31). Everything is under `port/`, plus this note, the screenshot and the HANDOFF. No game `.c`
changed.

## 1. The heap break at the switch to level 0x21: root cause = the stubbed inflater

**Symptom (P31):** with `?lvlload=1`, `heapwatch` broke inside `allocate_memory` called from the PC
func_150031EC at VI frame 722: block 1063E6E0 "size 63F938" outside the heap. It reproduces in node too
(`PORT_LVLLOAD=1 PORT_HEAPWATCH=1 port/web/boot.sh 40`, about 16 s).

**Diagnosis:**
- The PC func_150031EC was checked again against the asm, instruction by instruction. It matches, including
  the asm quirks: `bzero(D_800B1240, count)` (bytes, not words), and `D_800B0E00` really is 0x800B1210
  (`%lo` = 0x1210; the label file already places it there, so the overlap with D_800B1214..121C is the N64's own).
  The asset key is (4, level): a3 = 2 keys, then sp+0x10 = 4 and sp+0x14 = level. P31's note said (2, level).
- A heap dump before the first allocation showed the heap **already broken**: the header after the
  level's model-list buffer (1063BC94 + 0xC + 0x3A40 = 1063F6E0) held `next 20C80024 prev 0063BC94 info 10640938`,
  i.e. heap pointers with 0x10000000 added or masked off.
- The model list itself was **all zeros**, and func_1502B6BC returned count 3892 (0xF34). Asset (4, 0x21) is a
  rzip file (info 0x100015CE). func_1502B350 DMAs it and calls the C wrapper func_10006530 → **func_1000654C**,
  Rare's inflater, which is hand-written asm (init_eu_5DA0.s, its state lives in $f16..$f18) and was a **weak
  stub**. Nothing was inflated, so every compressed asset loaded as zeros.
- The C func_1502B4A8 (count 0) then searched the zero table for an entry with bit 31 set, found one 0xF34 entries
  later, past the 0x3A40-byte buffer, and "relocated" (`e[0] += base`, `e[1] &= 0x0FFFFFFF`) the next heap block
  headers. That is the corrupting write. The loader and allocate_memory were innocent.
- A direct Python decode of the ROM asset (scratch tool) gives the real table, which ends after 7 entries:
  `{0x38, 0x1878} {0x18B0, 0} ×3 {0x18B0, 0x9B8} {0x2268, 0x9E8} {0x2C50, 0x80000DE8}`.

**Fix: TEMPORARY PC func_1000654C in `port/ultra/pc_mem.c`**, written from the asm entry (58 lines):
- the stream starts at src + 2 if the first BE halfword is 0x1172, else at src + 4;
- the output limit is 0x70000000, lowered to src − dst when src > dst (in place) and to `limit − dst` when that is
  ≥ 0 and smaller;
- it returns the number of bytes written (the asm's $f17), or 0 on error.

The existing raw-DEFLATE decoder (`inflate_raw`) gained a vbe mode (`INB` / `OUTB`: byte A at A ^ 3), so it
inflates game memory in place with no copy. `[inflate]` logs the first 8 calls and every failure.

**Result:**
- Level 37 (the boot screen): asset (4, 0x25) found, 4 entries, D_800B0E00[0] = 1062A398 (P31: "not found").
- Level 33: 7 entries, D_800B0E00[0] = 1063CF00.
- Node 60 s with `heapwatch`: no break, `[heap]` 0 errors, 7/7 self-tests PASS, 1 link warning (the old one).
- Real-time Chrome (Metal, 45 s, `heapwatch=1`): past the switch, no break, no RuntimeError.
- No `[inflate]` failure in either run.

**The PC level loader is now the default.** `?nolvlload=1` (`PORT_NOLVLLOAD=1`) restores the stub; `?lvlload=1`
is a no-op now. Without `dlapprox` the frame is unchanged (0 triangles), because the asm func_150A5858 that would
draw D_800B0E00 is still a stub.

## 2. Level geometry on screen

`?dlapprox=1&freecam=1` draws level 0x21: **a round wooden floor**, 288 triangles (two materials, 144 each, CI8
32x64 textures with an RGBA16 TLUT), lit vertex colours fading to black at the rim. Screenshot
`P33_screenshot.png` (`port/web/shot.sh OUT.png 'app=game&dlapprox=1&freecam=1&heapwatch=1' 45000`, Metal).

### Why every screenshot since P21 showed a plain colour: fixed

`pc_video.c` cleared the canvas to the animated "main loop alive" colour on **every VI frame without a gfx
task**. The game draws at 25–30 fps or less in Chrome, so the canvas showed that colour most of the time, and so did
the screenshots. The renderer itself was fine: `glReadPixels` of the drawn frame showed the floor. It now clears
only until the game's first frame (`preserveDrawingBuffer` keeps the last frame). P21–P31's "clear colour"
screenshots were probably this colour too.

### Free camera (diagnostic, opt-in)

The game's view stays eye = at = (0,0,0): no camera target object is spawned (P31). With **`?freecam=1`**, the
renderer replaces the world view, which is the `G_MTX` projection **multiply** that follows the projection load
(`DA380005 <D_800DC6D0[buf]>`; the game multiplies its view into P), with a fly camera:
- input: pad 0, i.e. P27's input layer;
  - stick (WASD): move and strafe;
  - C-buttons (IJKL): look;
  - R (E) / Z (Q): up / down;
  - Ctrl: half speed.
- The game still receives the pad. Only the renderer's matrix changes.
- Start pose: `fcx/fcy/fcz` (world units) and `fcyaw/fcpitch` (degrees; yaw 0 looks down −Z). Without them, the
  camera is placed outside the bounds of the previous frame's vertices, and it follows the scene until the first
  input. So it re-frames at the level switch: level 37's backdrop is ±10000, level 33's floor is ±240 at y = 0.
- `[freecam]` logs the pose every 120 tasks.
- **Verified** with real key events: `PROBE_STEPS="18000:keydown:KeyW; 21000:keyup:KeyW; 21500:keydown:KeyL; …"`
  moved (0,168,528) → (0,143,460) and turned yaw 37.8°.

### New diagnostic: `?drawlog=N`

`?drawlog=N` prints one `[draw]` line per GL draw call of gfx task N:
- the viewport;
- the vertex count, the vertices with w ≤ 0, and the NDC x/y/z box;
- geometry mode, othermode, combiner, texture tile, prim/env/fog colours, and vertex 0;
- after the frame, a 5x5 `glReadPixels` grid.

Caveat: the state words are read at flush time. They can already belong to the next batch; the GL state used for
the batch is the one at its start.

## 3. What the level frame uses, and what the renderer still gets wrong

Level 0x21 frame (task 300, `dltrace`): projection `1.7113 / 2.1445 / -1.0202 / -101.01` (near ≈ 50), then the
view multiplied into P, then MV identity. Lights come by `G_MOVEMEM 0x0A` (48-byte records at offsets 0x00, 0x30,
0x60, 0x90). There is a Rare `G_MOVEWORD` index 0x10 block (12 words). The level DL then has:
- `D7000002 FFFFFFFF`;
- CI8 32x64 textures with a TLUT, loaded by `FD/F5/F3/F0/F2`;
- combiner `FC121824 5531FEFF` (TEXEL0 × SHADE), othermode `EF08AC3F 00552230`;
- geometry `ZBUFFER | SHADE | CULL_BACK | LIGHTING | 0x200000`;
- 9 × `G_VTX` of 32 vertices with Conker TRI4 (0x10–0x1F);
- no fog.

The precise list of what is still wrong or unverified:

1. **No visibility culling of the level.** func_150A5858 (hand asm, private registers) is a stub. `dlapprox`
   draws all of D_800B0E00[0], as func_1510BF50 does for levels 0x14/0x32/0x33. The LOD parts D_800B0E00[1..3]
   are never drawn.
2. **G_CULLDL (0x03) is ignored, and G_BRANCH_Z (0x04) always takes the near branch.** There is no LOD and no
   bounding-volume culling.
3. **Lighting formula not checked against the ucode.**
   - Unchecked: `rgb × min(1, ambient + Σ max(0, n·l) col)`, the normal from the 0x0E array, and the
     light-index mapping `n = len*8/48 − 2`.
   - The level frame sends `DC08000A` / `DC08060A` (offsets 0x00 / 0x30), which map to n = −2 / −1 and are
     **dropped**. They are probably Rare's lookat or reserved records.
   - `DC280C0A` / `DC28120A` become lights 0 and 1.
   - The floor comes out dark orange; whether that matches the N64 is unknown.
4. **Rare `G_MOVEWORD` index 0x10** (12 words per frame, for example `DB100010 95987760`, `DB100024 00650000`) is
   **ignored**. Its meaning is unknown: maybe point-light or specular parameters.
5. **Texture filtering:**
   - GL bilinear stands in for the RDP's 3-point filter;
   - no mip/LOD (`tex_level`, `G_TL_LOD`, `prim_lod` as a level), no detail or sharpen;
   - a tile with both a mask and clamp is approximated by GL clamp or repeat;
   - the half-texel `uls` = 0x402 of the floor tile is passed through but not checked.
6. **The CI-as-RGBA rule** (P8: 4/8-bit RGBA tiles read as CI) is a heuristic. This floor sets TLUT mode itself
   (`EF08AC3F`, bit 15 of the high word), so it is not exercised here.
7. **Blender:**
   - only `FORCE_BL` → `SRC_ALPHA / ONE_MINUS_SRC_ALPHA`;
   - the blender's P/A/M/B selectors (fog blending, memory alpha, `CLR_ON_CVG`, `CVG_DST`) are not decoded;
   - there is no coverage, and no alpha dither;
   - decals use a polygon offset (−1, −2) in place of the RDP's z-delta compare.
8. **Depth:**
   - GL depth from clip z replaces the 18-bit RDP z;
   - `G_SETPRIMDEPTH` (0xEE) and `G_ZS_PRIM` are ignored;
   - the z-buffer clear is recognised only as a fill rect with cimg == zimg.
9. **Fog:**
   - per-vertex `z/w * fog_mul + fog_off`, mixed in the shader only when the blender's cycle-1 P is 3;
   - not exercised by this level (no `G_FOG`); Rare's fog setup is not validated.
10. **Clipping:**
    - the GPU clips in clip space;
    - the N64's guard band and clip ratio (`G_MW_CLIP` `DB04xxxx`, ignored) and its near-plane behaviour are not
      modelled;
    - culling uses the post-divide cross product, with the w < 0 sign flip.
11. **`G_MW_PERSPNORM` (`DB0E`) is ignored.** That is harmless with float math.
12. **The viewport has overscan.** The game's Vp is 302x226 at (146, 108) on a 292-pixel cimg. It is scaled by
    canvas / cimg with H = cimg × 0.75 (219 against the 216 lines the projection assumes), so the image is
    slightly stretched.
13. **Combiner:**
    - one generic shader;
    - the second pass's `FFB3FF/FF64FE7F` (2-cycle-style selectors in a 1-cycle mode) and the K4/K5/noise inputs
      are not handled;
    - LOD fraction = `prim_lod`.
14. **Texture cache:** keyed by the TMEM generation, so every load re-decodes. This is a performance issue, not a
    correctness one.
15. **The level's colours and the floor's real look are not compared with an N64 capture.** No reference frame
    is available in this environment.
