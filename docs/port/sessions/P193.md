# Session P193: level 0x29 green patch = texture-cache collision between mip tiles 1 and 3 (branch `port-web`, 2026-10-24)

Renderer session (port/ only, no src_eu edits, no merges). Scripts in `docs/port/sessions/p193/` (build.sh, newgame.sh,
padwalk29.py copied from p189; crops.py = labelled crop montage; shots.sh = before/after runs). Logs in `port_work/p193/`
(Chrome chA..chH, shots/).

## 1. Result

- **Root cause**: the GL texture cache (`tex_for`, port/gfx/gfx_f3dex2.c) was direct-mapped on
  `(k0 * 2654435761 ^ k1 * 40503 ^ k2 * 97 ^ k3) & 255`. In a standard mip chain tile 1 (tmem 080, line 2, 32x16) and
  tile 3 (tmem 0A8, line 1, 8x4) give the same slot for every TMEM generation (low byte of `k2 * 97 ^ k3` is A0 for both;
  k0 / k1 are equal). apply_state binds tiles 0..5 to units 0..5 in order, so binding tile 3 **re-uploaded the GL texture
  already bound to unit 1** (logged: `mat 48 unit 1: tile 1 gl 173 hash 233` / `unit 3: tile 3 gl 173 hash 233`).
  LOD level 1 then sampled an 8x4 image with 32x16 addressing; texelFetch outside the image returns 0, i.e. alpha 0.
- The level 0x29 ground under the green patch is draw 48: CI4 64x32 + 4 mips, 2-cycle LOD (cc 26A004/151092FF),
  ALPHA_CVG_SEL. Its texels are all opaque (CPU decode), but at 1.5-4 texels per pixel it uses LOD level 1 (T0 = tile 1)
  -> alpha 0 -> discarded. Through the hole the first draw of the frame showed: the backdrop quad (+-1750, z -1000,
  RGBA32 4x256 gradient, cc FFFFFF/FFFCF279), uniform 00C700 there.
- The CI8 leaf cut-out (cc 26A004/15FC92F8) that P189 blamed is draw 49, drawn on top and correct (its views behave).
  P189's misattribution came from a logging bug: **`[draw]` lines printed the globals at flush time, i.e. the next
  draw's state** (flush runs after the new state commands). Fixed: apply_state saves the drawn state (`dl_st`) and the
  line prints that; lines also carry the draw index (`[draw] #N`).
- **Fix**: mixed hash (xor-multiply-shift over k0..k3, top 8 bits), 8-way probing, and an entry bound by the current
  apply_state (`tc_stamp`) is never evicted. `?p193oldtc=1` restores the old direct-mapped cache (used for the "before"
  shots). Any LOD material whose tiles 1 / 3 collided was affected (every 2-cycle mip chain with this layout).

## 2. How it was found (useful for the next renderer bug)

1. `?p193dbg=F` views on the cc 15FC92F8 draws changed only torches / fence rail, not the patch (chB) -> not that draw.
2. `?p193idx=F` (every draw coloured by its index for 100 retraces, r/g/b = idx bits 0-2/3-5/6-8, 32 per step + 16) +
   `?p158f` dump in the same run (chC): patch = draw 0 (16,16,16), leaves = draw 48 colour... (index from the log).
3. `?p193bucket=F` (draws 16k..16k+15 in index colour per 100-retrace window; chF) and `?p193pick=F[&p193d=D]` (per-index
   views of draw 0 and draw D: hidden / magenta / shade / T0 / alpha; chG): draw 0 = the backdrop, magenta exactly in the
   patch; draw 48's T0 / alpha mostly 0 in GL while its CPU-decoded tiles were opaque -> GL binding problem.
4. `[p193] mat N unit k: tile, gl texture, hash, hit/miss, first texel` in p158 dumps (chH) showed the shared GL texture.

New DIAGNOSTIC flags (all off by default): `?p193dbg=F` (+ `p193cc0` / `p193cc` decimal combiner words; views 0 normal,
1 T0, 2 shade, 3 magenta, 4 LOD_FRACTION, 5 lt / texon / distant, 6 final alpha, 7 T0.a/T1.a, 8 hidden), `?p193idx=F`,
`?p193bucket=F`, `?p193pick=F` (+ `p193d`), `?p193oldtc=1` (TEST: old cache). p158 dumps now log G_VTX of untextured
draws too.

Chrome timing note: shots are wall time; retrace ~ 50 * t - 70 and the screenshot lands ~1-1.5 s after the retrace
window starts (use 2-s windows, read the window from the image content). `newgame.sh` needs `P103=` (empty) for the real
route; with the default `p103boot=1` the run crashes at 17820 (level 6 scene 20, __wrap_func_1502457C OOB, chA).
