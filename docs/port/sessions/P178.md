## 1. The producer: asm stub func_150170C4 (game_eu_44010.c)

`stscan.py` (linear constant propagation over every `asm/**/*.s` instruction word: lui / addiu / ori / addu / or, reports
stores whose base+offset hits 0x800D2520..0x800D252B and calls with a0..a3 in 0x800D2000..0x800D252B) finds exactly one
writer of each word in the whole ELF:

    STORE game_eu_44010/func_150170C4.s 15017114 sw $v0, 0x0($s2) -> 800D2524   (D_800D2104)
    STORE game_eu_44010/func_150170C4.s 15017138 sw $v0, 0x0($s5) -> 800D2528   (D_800D2528)

(plus func_15016950's D_800D2520 / D_800D2521 byte stores). No data table holds either address. func_150170C4 is a
`#pragma GLOBAL_ASM` stub in the port (hit once per level load since boot, `[stub] func_150170C4 ... frame=1`); its only
caller is func_15016950 (level setup load, converted C, game_eu_44010.c:129). So in the port both pointers stay NULL
forever; nothing else writes them (the runtime log `[p178path] ... stub` / P174's `[p174ptr]` at 10733 both show NULL;
no store-watch needed: the static scan covers every store with a constant or lui-derived base).

What it does (asm EU 0x150170C4..0x150172A4), **level_load_spawn_paths(level)**, one entry per spawn record
D_800D20FC[0..D_800D2520):
- D_800D2104 = allocate_memory(n * 4, 1, 0, 0), D_800D2528 = allocate_memory(n, 1, 0, 0), both bzero'd;
- player records i < D_8008FD8C (s8): D_800D2104[i] = allocate_memory(0x10, 1, 2, 0) (bzero'd), D_800D2528[i] = 2;
- func_1502B7F0(&asset, 2, 0x10, level) != 0: for i in D_800D2521 .. D_800D2520-1, entry e = asset + (i - D_800D2521) * 8
  = {s32 offset, s32 count}; if offset != 0: D_800D2528[i] = (u8) count, D_800D2104[i] = asset + offset.
  (path points are s16[4]; func_150623F4 reads +6.) v0 is garbage; the caller ignores it.

**Route: convert slot** (asm -> C, ~0x1E0 bytes, no jump table; difftest-able). The port test body is
`port/gfx/p178_path.c` c_150170C4 (vbe_ld8 / vbe_st8 for the byte tables). Logged results (`[p178path]`), e.g. level
0x18: 25 records (5 fixed), paths at 6..: (-254,-291,2297) (247,-289,2278) (53,-368,1658) ...; level 6: 52 records,
counts up to 22; level 0x29: 14 records, counts 1..14. Producer before consumer: func_150623F4 / func_150611E8 /
func_15056B08 (game_83300.c) and the game_A28B0.c path code read them.

## 2. With ?p178fix=1: scene 3 runs, the intro goes on, then a loop on level 0x29

Node fixA/fixB (`PORT_P174FIX=1 P171FIX=1 P174EV=1 P178FIX=1 P103BOOT=1 HEAPWATCH=1 P78NULL=1`, new-game PADF): no trap at
10733. Route: 10725 BF starts scene 3 (on **level 0x1D**, `1003(1, 0x1D)`), 14729 scene 4, 15809 scene 2, 17813 level 6
scene 0x14, 19119 level 0x18 scene 2, 20181 scene 4, **22765 BF sub 0x1E8: `5000(7, 0x29)` -> level 0x29**. Then level
0x29 reloaded every 4 retraces (795 loads) until the heap broke at 24343 (`[heapwatch] heap broken`, trap in
func_15002008).

Cause (fixB/fixC/fixD `[p178bf]`): two copies of BF run (blocks 10b4eb00 from 4559, 10b47a90 from 19119), both with
+0 flags **0x0800, id 0**. func_1509B704(0xBF) never finds them, so `50BF(1)` (finish: save bit set, then stop) sets
the bit but cannot stop the event; func_1509B5AC loads a duplicate on each start, and BF's state 3 keeps re-issuing
`5000(7, 0x29)` from level 0x29. Every event struct in the port has id 0 (C9 -> 0x1000, C8 -> 0x1000, CB -> 0x5000;
unk2 = level is set).

**Root cause: a vbe stack-layout bug in func_1509B8FC (game_C8950.c, event_load)**. wasm (`llvm-objdump` of
vobj/game_C8950.c.o): frame 16 bytes; the s16 parameter copy is stored at (sp+14)^2 = **sp+12**; `s16 sp18[2]` is at
**sp+10** (2-aligned) and passed to func_1502B5C8 as its `s32 *` out-param; func_1502B5C8's `*q = 1` / `*q = size`
32-bit stores at sp+10..13 overwrite the parameter copy, then `unk0 |= arg0` ORs the high half of the size (0). On N64
sp18 is 4-aligned and the parameter lives in a register. vbe.py pads/aligns globals to 4 but leaves `alloca ..., align
2` as is, so any sub-word stack slot next to a 2-aligned array used as a word can collide the same way.

Fix routes: (a) general, port tooling: vbe.py raises every `alloca` with align < 4 to align 4 (each slot then starts on
a word, xor 2 / xor 3 stays inside its own word) - needs vbe.stamp removal and a full port rebuild + regression; (b)
local: func_1509B8FC's out-param as `s32 sp18` (src_eu; it is a NON_MATCHING body). Test used here: `?p178evid=1`
(p103_boot.c wrap of func_1509B5AC) ORs the id back into +0 after the start (list order and the entry-0 save-bit check
still used id 0).
