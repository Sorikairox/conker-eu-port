## 1. func_15001460 (game_2DF70): triangle scan of a level DL

`void func_15001460(s32 dl)` walks 8-byte commands until G_ENDDL (signed byte -0x21):
- **G_VTX (0x01):** address w1; when its segment (bits 24-27) is non-zero:
  `D_800D3048[seg] + w1 - (D_800D3088 << 24)` (D_800D3088 is 1 while func_15003668 scans object DLs). n = (w0 >> 12) & 0xFF,
  v0 = ((w0 >> 1) & 0x7F) - n; the cache loop runs **from v0 to n - 1** (not v0 .. v0 + n - 1), stride 16. Faithful;
  harmless for v0 = 0.
- **G_TRI1 (0x05):** index bytes 1-3 >> 1. **G_TRI2 (0x06):** 5-bit fields at bits 17 / 9 / 1 of w0 then w1.
  **0x1x (Rare TRI4):** w1 >> 25 / 20 / 15 / 10 / 5 / 0, w0 >> 10 / 5 / 0, w0 >> 23 / 18, and
  `((w1 >> 30) & 3) | ((w0 >> 13) & 0x1C)` (all & 0x1F).
- Per triangle at index D_800DBE38: D_800DC26C[3 * i + k] = vertex pointer; D_800DC270 (8 bytes) = {x min, z min,
  x max, z max}; D_800DC274 (4 bytes) = {y min, y max}. With D_800DBE63 set: min -0x8000 / max 0x7FFF.
- **The bounds are recomputed only when cache entry 0 (not the triangle's vertex) is above 0x100000.** Otherwise the
  asm writes its stale stack slots again (the previous triangle's bounds, or whatever an earlier call left there for
  the first one). The C keeps the previous values and starts at 0. In practice this happens for every area-2 (object)
  triangle: func_15003668 clears segment 1 (D_800D304C = 0), so object vertex pointers are offsets. The game's
  object update recomputes those bounds later (func_150A49D0 path). The harness masks exactly these bounds (below).
- The vertex cache is `s32 verts[35]` (the asm frame has 35 words at sp+0x94). Indices are 5-bit, so only a VTX with
  v0 < 0 or n > 35 could overflow; no real DL does (the harness would fault or differ).

## 3. func_150183D0 + func_150184B0 (PVS index; hand asm, game_eu_45B90)

Called by func_150025FC when the level has the PVS assets (2, 5, level * 2) (bit stream) and (2, 5, level * 2 + 1)
(table: tree size, then 256 x {u32 code, u32 length}). func_150184B0 is called with the caller's registers (it
reads the table from the caller's stack slot and returns through $s4); in C it is `void func_150184B0(s32 *table)`.
- func_150184B0: D_eu_800BE9F8 = allocate_memory(table[0]); 6-byte nodes {s16 symbol or -1, s16 child-0 offset,
  s16 child-1 offset} (offsets from the tree base); codes are inserted MSB first; a leaf met on the way is pushed
  down until the two codes differ (shift counts & 31, as srlv / sllv).
- func_150183D0(rowlen, rows, stream, table): D_800BE5D0 = stream; D_eu_800BE9F4 = allocate_memory(rows * 4);
  for each row it records {byte index, bit} (the first row {-1, 0}) and then skips `rowlen` symbols (decoded symbols
  are discarded). Both loops are do-while as in the asm.
- Test: only through the level harness (private calling convention). Levels with a PVS: 0x2, 0x6, 0x7, 0xB, 0xC,
  0x13, 0x17, 0x1A, 0x1B, 0x1D, 0x1E, 0x24, 0x2B, 0x2C, 0x2D, 0x30, 0x34, 0x37, 0x3C (0x1C has the table but no stream).

## UNVERIFIED (browser runtime)

- **Vertex pointer tests:** func_15001460 (`> 0x100000`), func_15002008 and func_15002248 (`> 0x80000000`) treat
  smaller values as "no vertex". In the browser, real heap pointers may be below 0x80000001 (P37 saw 0x10906000), so
  every triangle would become (0, 0, 0) in the quadtree box tests (every leaf then lists every triangle near the
  centre box) and the bounds would go stale. The wasm port needs these pointers in the N64 kseg0 range or the
  tests adapted (port-side `#ifdef`).
- func_15001A08 reads PI_STATUS and the cart word through IO_READ (0xA4600010, 0xB0000D24 | osRomBase): the web
  layer must answer them (0 / the ROM word) or the loop never ends / the pool doubles.
- Area-2 bounds: the asm's are stack garbage (§1); C writes 0 until the object update refreshes them.
