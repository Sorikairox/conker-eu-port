## 2. Why nothing was drawn before, step by step

`?p46check` showed func_1502BDC0 appending only its two G_DL commands per mode (modes 1 and 2; record 0: state 1,
id 0, unk5 0, +0x74 0x0E, alpha 255, +0x1D4 set). func_1502CC64 → func_1502CFEC: func_1503DD8C (C) returns
func_150844AC's result (stub), then CFEC returns early because the vertex block word is 0. With the PC func_150844AC
the DL appears (24 commands per object in mode 1); the bones then needed func_150A9E64.

func_150844AC, read from the asm: `rec = o[0x65] ? D_800CC2D0[o[0x65]-1]+0x144` (the asm's `D_800CC508 + 0x32C *
o[0x65]`, EU addresses) `: o+0x144`; `slot = o->+0x2C4[var]`; mode = `rec[0x10] & 3` (slot 0 → 2); returns 0 when both
words are set or `D_800D19A0[slot]` is NULL; mode 0 shares the block (`D_800D1F80[slot] += 2`), mode 1 shares it for
the first user and copies it (`allocate_memory(D_800C5BC0[slot] * 16, 1, 2, 2)` + bcopy) for later users, one word
for both frames; mode 2 does it per frame word (+1 per share), and on an allocation failure of the second word frees
the first. Result 1 = allocation failed.
