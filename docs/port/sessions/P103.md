Sequence:
1. `func_15007830` (entry) -> **func_151E582C**: settings defaults, save record D_80090174, mode 11, level 0x25.
2. **Mode 11 / level 0x25** (func_151DEBB4 + render func_151EC300): red text line (t < 200), logos + 14 legal lines
   (t < 450), 64x64 image (t >= 450). START skips ahead (0x119..0x190, 0x1F5..0x258). `osTvType` (D_80000300) != 0,
   i.e. an NTSC/MPAL console, freezes the timer and blanks the screen: the EU region lock. The port has osTvType 0
   (PAL), which is right. At timer 0x2C7: `D_800E0B94 = 1`, `func_1501C710(6, 0x21, 0, 0, 1)`.
3. **Mode 1 / level 0x21 = the logo screen.** The level-start event pass (func_15017868 -> func_1509B4A0) finds
   one level event: **id 0xC9, named "LogoScreen"** (D_800877D0[0xC9] = {name 0x8009F468, 0xA0000000, level 0x21,
   prerequisite list empty}). Its event script (asset 20 / 0xC9, run by the event VM func_150ADFD0 every frame through
   func_1509BBA0) drives the logo sequence and the move on. That last part is not proven here (the VM is asm), but the
   only exits from level 0x21 in the code are event / scene actions: scene opcode 0x67 in func_15024910 calls
   func_151DECB4 (-> mode 3, level 0x1D: menu); the game-state action handler func_1509FD30 (D_80088874 entry 4,
   event ids 0x5xxx) has the attract idle check func_151E89C0 (-> mode 8 -> 9 -> back to 0x21) and func_151E5528
   (-> mode 10).
4. **Mode 3 / level 0x1D**: title / main menu (func_151DEDD0, asm).
5. Starting / continuing a game: func_151E3864 (chapter from the save through func_1509D338 / func_1509D49C) or
   func_151E3A1C -> **mode 0**, level from the save, and the code checksum func_151E86A4.

Nothing on this path reads a debug flag, a controller-pak, the EEPROM or osResetType to choose level 0x21. Only
osTvType matters (NTSC lock).

## 2. Why the port sits on level 0x21

**Mode 1 / level 0x21 is the correct next step** after the boot screen: same code path as on N64. The port stops
there because **the level event system is asm**, so the "LogoScreen" event never starts.

Evidence (`idle.log`, `?p103boot=1`, 35 s, no input):
```
[p103] frame 715: mode 1 (prev 11) level 25 timer 0 tv 0 | objects 0 events 0 scene0 0
[p103] func_1509B4A0(33, 1) frame 722 level 21 mode 1: 1 level events, save flags 10635030
[p103]   event 0: id C9 rec 105B1468 A0000000 00210000 105B0840 105B0840 prereqs [FFFF ] -> asm would answer 1
```
- **func_1509CBD4** (game_eu_CA630.c, asm stub, 48 insns) is the prerequisite check. The stub answers 0, so
  func_1509B4A0 never calls func_1509B5AC. From the asm, an empty prerequisite list answers 1.
- With `?p103ev=1` (a C version of func_1509CBD4 in p103_boot.c, test only; `ev.log`), func_1509B4A0 goes on to
  `func_1509B5AC(0xC9, 1)` at frame 722, which is **also an asm stub** (`[stub 39] func_1509B5AC`). No event record
  is created, so func_1509BBA0 / func_1509BA04 (C) have an empty list D_800D2F48, and the event VM func_150ADFD0
  (asm) is never even reached. No RuntimeError.
- START at 20 s does nothing, in both runs (no event, no mode change).

Also found:
- **World objects are 0 on every level because of a stub, not the level data** (this corrects P101): D_800DC320 is
  written only by **func_150039E0** (game_30E90.c, asm, 741 insns, called by func_15007B3C right after the model
  loader). It loads assets (0xB, level) and (0xC, level, 2) in 0x44-byte records into D_800DBEF4. Level 0x21 has
  both assets in the ROM: 0xB is 0x33 bytes and 0xC is 0x1EC bytes, as stored.
- The scene system never starts on level 0x21: no func_1501D348 call in 35 s. Scenes there would come from event
  actions.

### Mode 0 and the raw pointer D_8009018C[0] (P101's question)

- `D_8009018C[0]` stays the raw N64 address 0x151DE100. The cause is that `func_151E86A4` (the anti-tamper code
  checksum, game_eu_20B730.c) declares `extern s32 func_151DE100` and sums the code bytes from &func_151DE100 to
  func_151DECB4.
  - So func_151DE100 is a data symbol in the port: a zero-filled `unsigned char func_151DE100[0x100]` in
    data_stubs.c (vbe.py keeps it out of FUNC_AS_DATA).
  - n64mem.py therefore skips that relocation word ("F-data" type clash). `n64mem_report.txt`: `game_data F-data 1`,
    and this is the only one.
- The pointer is **not skipped, mis-dispatched or silently stubbed. It is never reached:** mode 0 is entered only
  by func_151E3864 / func_151E3A1C, after the menu.
  - When it is reached, the icall trampoline gets `__port_fsig(0x151DE100) = 0` (index >= FSIG_MAX). That takes the
    fast path, `call_indirect` with table index 0x151DE100, so it fails with **RuntimeError: table index is out of
    bounds**.
- func_151E86A4 runs on the same mode-0 entry and would also misbehave in the port.
  - Its loop runs from a wasm data address (about 0x10xxxxxx) up to a function-table index (about 0xCA7). It never
    iterates, so the sum is 0, not 0xBB9FE01C.
  - It then executes `*(s32 *)osSpTaskLoad = 0`, which writes 0 at the wasm address equal to osSpTaskLoad's table
    index (the null zone).

## 3. What to change, in order (producers before consumers)

1. **Level events, one unit** (1 alone only reaches the next stub; 1 to 3 alone creates records that a stub VM
   runs):
   1. func_1509CBD4 (game_eu_CA630.c, 48 insns): the prerequisite check. Reference: `p103_prereq` in
      port/gfx/p103_boot.c, written from the asm.
   2. func_1509B950 (game_C8950.c, 45 insns: relocates the event block loaded by func_1509B8FC).
      - **Bug in C:** func_1509B8FC is `void`, but its asm caller func_1509B5AC uses v0, which is func_1509B950's
        return value (a dropped return, P75 lesson).
      - It must become `struct249 *func_1509B8FC(s16)` returning func_1509B950(temp_v0).
   3. func_1509B5AC (game_C8950.c, 86 insns): start event `id` (func_1509B704 lookup, B8FC load, B810 insert, first
      run of func_150ADFD0(e, 0) unless its save bit is set; flags 0x400 / 0x4000 / 0x1000 / 0x800).
   4. func_150ADFD0 (game_eu_DB7E0.c, 485 insns: the event script VM; indirect calls through D_800D3C64), with
      func_150ADA20 (18) and func_150AE760 (55).
2. Re-run `?p103boot=1` plus the stub census on level 0x21 to get the LogoScreen script's action handlers. Candidates
   (asm):
   - func_1509FD30 (game_eu_CD540.c, 367 insns, game-state actions 0x5xxx: level change, func_151E89C0,
     func_151E5528);
   - the other asm entries of D_80088838 / D_80088874 (func_15097E9C already shows up per frame).
3. func_150039E0 (game_30E90.c, 741 insns): the world-object loader. Every level has 0 world objects without it.
4. Mode 3: func_151DEDD0 (game_eu_20B730.c, the title / main-menu handler on level 0x1D). Its render
   func_151ECB98 is C.
5. Mode 0 (story): func_151DE100 (game_eu_20B730.c, the mode-0 handler: PI DMA reads, pause text).
   - At the same time: under `#ifdef PORT`, skip the code checksum in func_151E86A4.
   - Drop the data use of func_151DE100 so that it is a function in the port: remove the data stub and the vbe.py
     note. n64mem.py then relocates D_8009018C[0] to its table slot.
   - A port-only fix before that is not useful: entering mode 0 needs the menu (step 4), and the handler would be a
     stub.

No port-side fix was made: the only port-side culprit (D_8009018C[0]) cannot be hit before step 5, and fixing it
needs the func_151E86A4 change in game C.
