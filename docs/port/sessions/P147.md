## 1. VI pacing: 50 Hz for PAL
Before: one browser frame (requestAnimationFrame) = one VI retrace, so ~60 retraces/s (120 / 144 on fast monitors).
The game counts everything in retraces (scene timers, the audio task: one audio frame every 2 retraces), so it ran 20 %
fast; and the audio overran: the audio manager (init_8F90.c func_10008F90 / func_100095A0) makes 920 samples per audio
frame at 22020 Hz (736 when AI_LEN >= 249), i.e. 21.5k..23k samples/s at 25 audio frames/s, but 25.8k..27.6k at 30.
Measured with the old pacing (`?vi60=1`, `port_work/p147/pace60`): ring 35k frames after 10 s, 113k after 35 s, full
(131071 = 6 s latency) and **15504 frames dropped** in one 5 s window after ~70 s.

Design (port/ultra/pc_sched.c `frame()`):
- `retrace()` = the old frame body (frame count, hooks, `port_vi_retrace`, run threads until blocked).
- Browser: fixed-timestep accumulator on `emscripten_get_now()` (performance.now): each main-loop tick adds the elapsed
  time, runs one retrace per period (20 ms when osTvType = PAL, `port_tv_type` set at boot in game_main.c; 1000/59.94 ms
  otherwise), then presents (`port_video_frame`) only if a retrace ran; the canvas keeps the last drawn frame
  (preserveDrawingBuffer), so 120 / 144 Hz ticks without a retrace just show the previous frame.
- Catch-up caps: elapsed time per tick clamped to 250 ms, at most 4 retraces and 33 ms of work per tick, backlog above
  2 periods dropped (a slow machine slows the game instead of spiralling). Pause / hidden tab (P27 `port_set_paused`)
  resets the clock: no burst on resume.
- Node (no `window`), `?det=1` and `?vi60=1`: one retrace per main-loop callback, as before (deterministic frame
  numbers; node steps as fast as its setTimeout shim allows). The `?det` clock now advances 1/50 s per retrace for PAL
  (was 1/60).
- `?timer=N` (N > 1): setTimeout main loop with an N ms period (test aid; `timer=1` = 16 ms as before).

Audio (port/audio/aud_out.c, pc_os.c): AI_LEN_REG / osAiGetLength now report the ring level **minus a target latency**
(3072 frames, ~140 ms; `?ailat=N`). The game keeps AI_LEN near 249 samples; with the whole ring reported the
ScriptProcessor (2048-frame bursts) would find the ring nearly empty every time. With the offset the ring settles at
~2.1k..5.3k frames.

Measurements (`?p147pace=1` / PORT_P147PACE=1: every 250 retraces, retraces per wall second and per audio second

## 2. VI mode and the presented rows
- `?p147vi=1` logs the game's VI mode (pointer captured in osViSetMode, D_8002AF20): PAL, ctrl 0x3116 (16-bit), width
  292, hStart 0x8C..0x2D5 (585 dots) xScale 0x200 -> 292.5 columns; origin 0x248 (= one 16-bit row), vStart
  0x3F..0x244 (258 lines per field) yScale 0x350 -> **213.7 rows, i.e. framebuffer rows 1 .. 214.7** of the 292 x 216
  framebuffer (126144 bytes). The game's own screen-adjust (func_10003C10 / init_49E0.c) edits this struct in place;
  the port reads it each gfx task.
- Renderer before: rows 0 .. 0.75 x width = 219 stretched on the 4:3 canvas, so row 216 (the stray line under the logo-
  end iris fills, P144) was visible. Now (gfx_f3dex2.c `vi_view_update` + pc_os.c `port_vi_view`) the canvas shows
  exactly the VI rows: viewport, scissor and rect NDC use `(y - VI_Y0) * canvas_h / vi_h`; offscreen images unchanged;
  `?p147vifull=1` = old mapping. Aspect: 585 x 258 of a 640 x 288 field ~ 1.36, so 4:3 is kept.
- Screenshots: before P147_1 (logo-end black with the orange row 216 line at the bottom), P147_2 (iris); after
  P147_3 (black, no line), P147_4 (iris on rows 1..214).
- **Logo-end title image (5/0x5C b5 0)**: `?dltracef=2060` / `2095` (new knob: trace the first gfx task at or after a
  retrace): the image is two TEXRECTs at 178..277 x 226..278 while the scissor is 2..290 x 0..216 and the framebuffer
  has 216 rows, so the RDP clips it on the N64 too: it is not a display-size problem and it is not shown on hardware
  in this position. Whether the N64 draws it elsewhere (scene data / a stubbed producer giving y) is still open.
