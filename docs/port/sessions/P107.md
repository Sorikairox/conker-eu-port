## 1. game_A28B0.c

- Line 21 of func_15075400 is `((u8*)D_800D154C->unk218) += 1;`. That is upstream code, in blame since the
  2026-10-17 import. The "P17" in the P105 note was wrong.
- srcfix.py (P23) already had a lvalue-cast rule, but only for `(T)x = v;`. The parenthesised compound form did not
  match it, so census.py marked the TU FAIL. GAME_OBJS only takes `ok` TUs, so the TU was dropped from the wasm.
  gen_stubs then gave every function a weak stub that returns 0, kind `absolute` (the names are in
  undefined_syms).
- The TU is the D_800D154C "current object script" interpreter: script byte-code readers and commands through
  `unk218`.
  - Callers from outside the TU: func_15056B08 (game_83300) -> func_1507BC14, and func_1506DB30 (game_981E0) ->
    func_15076760.
  - 4 ELF data words (0x80086BD0..0x8009A53C) point into it.
  - None of its stubs appears in the P107 before log or in any port_work/docs log. It is not on the 50 s frame path.
- Fix (srcfix rule `LCAST2`): `((T)x) op= v` -> `*(T *)&x op= v`. Line 21 becomes `*(u8* *)&D_800D154C->unk218 += 1;`.
  That adds one byte to the pointer, as IDO does.

## 4. port/tools/stubcalls.py

Usage is in the docstring. Run it from the worktree root after `eval "$(tools/eu_port/wt.sh env <wt>)"` and a port
build:
```
python3 port/tools/stubcalls.py [--log NODE_LOG] [--all] [--depth 3] [--out docs/port/stubcalls.tsv] [--func NAME ...]
```
- **Stubs**: port/stubs/asm_stubs.c. `!` marks a name that has a --wrap guard.
- **C functions**: the -O0 IR of the linked TUs (census ok, not excluded). NON_MATCHING comes from the src_eu
  `#ifdef NON_MATCHING` / GLOBAL_ASM `#else` scan.
- **Per function**:
  - `direct`: stub calls;
  - `table`: indirect calls traced to a global table, whose targets are the function words in the EU ELF data,
    as in arity_scan;
  - `addr`: stub addresses the function takes;
  - `unk`: indirect calls whose target it cannot resolve;
  - `deep`: stubs reached through C->C calls.
- **Hits**: from the last census block in --log.
- **Check**: every one of the 49 hit stubs has a C caller in the tool's output. Two are guarded names
  (func_150000B0!, func_1509CBD4!). The P105 case shows up: func_15147CB0 (C) lists func_15148428@D_8008A5A0.
- **Limit**: it cannot follow data flow. func_151DA6F8 spawning particles that another C function dispatches later is
  not a call edge. Use --all and look at the dispatchers.
