## 0. P97's bisect builds were no-ops (lesson)

- `port/build/vbe.stamp` depends only on census / exclude / tools, **not on the game .c files**.
  - `vbe_build.py` recompiles changed TUs by mtime, but it only runs when the stamp is out of date.
  - So `git checkout REV -- conker/src_eu/X.c && run.sh build` prints "Nothing to be done" and links the old objects.
- P97's two bisect builds (`build_bisect*.log`: "Nothing to be done") tested the unchanged HEAD build. That is why
  "not P92" and "not func_150268BC" came out.
- **Rule: `rm -f port/build/vbe.stamp` before every build after a change to game C** (`port_work/p99/bis.sh` does it).
- Sanity check: all 44 changed sources back at e35cc6a with a real rebuild give the old camera (below); without the
  stamp removal they gave the new one.

`bis.sh NAME REV FILE...` checks out the files at REV, removes vbe.stamp, builds, restores the files, copies the build

### What changed

- Before, func_15124C38 was an asm stub that did nothing, so the camera target height +0x2C0 never moved:
  - at.y stayed 1.0 while the player stood at y 0;
  - it was still 1.0 while he fell to y -2174;
  - in the respawn scene it was 0.0 while he stood at y -2078.
- Now the target height follows the player, eased through func_150498A0:
  - y + 67.5 while standing;
  - lagging behind him while he falls (frame 885: player -3604, at.y -2907);
  - y + 67.5 in the scene (-2010.5 for -2078).
- The eye height stays at 400 the whole time (cam +0x2FC; it is written by another, still-stubbed path). So when
  Conker falls before the death, the camera tilts down after him: pitch -70..-77 deg. That is the "almost straight
  down" view in `p97/P97_before_after_33000ms.png`.
  - The old view (table and door) was the frozen stub target at y 1.
- The 41 s scene camera "sitting higher" has the same cause: the target is now at the player (+67.5) instead of
  y 0.
- P97's "0 calls" for its `?p97camh` wrap is explained: `--wrap` only catches calls from other objects. The callers
  of func_15124C38 (game_14FF90.c lines 1787 / 1969) are in the same TU, so the wrap never saw them, but the function
  runs every frame.

### Check against the asm (asm/nonmatchings/game_14FF90/func_15124C38.s)

The y selection was compared instruction by instruction with the C, all matching:
- the +0x2C bit 0x80 / func_15125490 branch (0.25 offset);
- +0x84 bit 0x20000000 -> floor +0x180;
- the D_800C3671 / +0x137 / +0x84 == 0x194 / +0xAD == 1 branch -> y;
- the `-10000 == +0x360`, +0x84 bit 0x200000 (sll 10 / bltz), +0x28 < 170 and +0x370 > 300 branch;
- the clamp of +0x28 * (1/300) to 0..1;
- the hang branch (+0x102, +0x370 < 100, +/-10 by +0x2FC);
- out / +0x23C;
- the speed / rate pairs 5/8, 5/9, 7/9, 4/8, doubled when +0x84 bit 0x200000 and y < +0x2CC;
- the func_150498A0 arguments (a1 = y, a3 = speed, stack rate, +0x7B4).

P92's difftest is EQUIV, with 31/39 mutants killed.

**Verdict: no fix. The C is correct.**
- The new view is the game tracking a falling player with a camera whose eye height is still fixed by a stub.
- The real defects are elsewhere, and both predate P93 / P95 (the e35cc6a build falls too):
  - the fall itself: the player drops from y 0 below the ground near (-179, 301) from about node frame 805;
  - the eye-height producer, which is still a stub.
- No game C change and nothing to port to `port`.

## 2. Audio: the mixer works; the game requests no sound in these runs

- In every run (P91 to P97, node and Chrome), the only sound start is id 0x15 from func_1508000C
  (game_eu_AC770.c). That is the floor-material ambient loop: flag 4 of D_8009BC80[mat][6], started when the player
  steps onto that surface.
  - Node P91 `boot1/2/3`: starts at frames 2457 / 2565 / 3713, player idle at (-104.6, 7.4, -741.9).
  - Node P97 `boot1/boot2/final`: 0 starts. The player ends at (-196.9, 39.6, -437.7); the walk is camera-relative
    and the camera / scene changed, so the path changed.
  - Chrome: P91 after / walk2 had a start (rms 0.022 / 0.024); P91 **walk3 had 0 starts and rms 0**, the same as all
    P94 / P97 runs. So P91's sound was a lucky position, not a working state that later broke.
- No music or other sound effect is ever started in any run (an older gap, probably the asm sound stubs
  func_10010154 / func_1000F568 in init_EB00, or the music trigger path; not traced).
- Proof that the audio path works at HEAD: new DIAGNOSTIC `?p99snd=F` starts sound 0x15 once at frame >= F through
  the game's own func_1000D96C.
  - Chrome, `port_work/p99/chsnd.sh port_work/p99/snd1 "&p99snd=1200" 45`: sound start logged at frame 1201.
  - Non-zero samples from t=27 s; at the end 709240 non-zero samples, **rms 0.026, peak 0.25, PASS**
    (`port_work/p99/chrome_snd1.txt`).
  - So mixing, the audio HLE, the 22020 Hz output (P95 fix) and Web Audio all work.
- **No regression and no culprit commit.** Next step for sound: find why no music sequence starts (the music start
  path and the init_EB00 asm stubs).
