## 1. ROM-offset symbols are absolute (`port/tools/vbe.py`, `abs_syms`)

The vbe IR pass now rewrites every reference to the data symbols that the N64 link places at
absolute addresses below RAM into a constant, and drops their `external global` declaration:

| symbol | value | use |
|---|---|---|
| `D_1A3B40` | 0x1A3B40 | texture bank base (func_1510D8F4, func_15003570) |
| `D_AB2240` | 0xAB2240 | asset table root (func_1502B020 / B110 / B8E0 / B9B4) |
| `D_2D810` | 0x2D810 | DMA source in game_eu_4A070.c |
| `D_11AF` | 0x11AF | a texture id passed to func_1510D66C |

`@D_x` becomes `inttoptr (i32 N to ptr)`, so `&D_x` evaluates to N everywhere (14 references in 5
TUs). The four `extern s32 func_X;` callbacks (`func_15033ECC`, `func_150D5634`, `func_150E394C`,
`func_151BB690`) are re-declared as functions, so `&func_X` is a function-table index (stubbed and
registered like any other function) instead of a zero-filled data stub. Data stubs: 14 → 6. The
6 left are the ucode text labels (`D_10029400`, `D_100294D0`, `aspMainTextStart`), `D_1002AAD0`
(osInvalICache range), `__osExceptionPreamble` and `func_151DE100` (read as code bytes); none of
them matters on the PC.

**Verification** (boot self-test `port_romsym_test`, `pc_overrides.c`; in node and Chrome):

- the game's C `func_1510D8F4(0xED0)` returns 0x6F1618;
- a PI DMA of 16 bytes from there gives `00000300 ED4F2156 4331…`, the bytes Python reads from
  the ROM at 0x6F1618 → `[romsym] PASS`;
- after init, `D_800B8BB8` (the inflated-size table that the C `func_15003570` builds by DMA from
  `&D_1A3B40` at boot) has texture 0xED0 = 768 and texture 0 = 1536, matching the rzip headers →
  `[romsym] size table PASS`.

## 2. KSEG0 pointer tests (`vbe.py`, `k0_checks`)

Rare's audio code tells a resident pointer from an unloaded reference with
`(p & 0xFF000003) == 0x80000000`, and a RAM pointer with `K0_TO_PHYS(p) <= 0x800000`. In the port
both tests fail for every wasm pointer, so the ADPCM decoder emitted ClearBuffer for every voice.
The IR pass rewrites exactly these shapes:

- `and p, 0xFF000003` + `icmp eq/ne 0x80000000` → `and p, 0xF0000003` + `icmp eq/ne 0x10000000`;
- `and p, 0x1FFFFFFF` + `icmp ugt 0x800000` → `icmp ugt 0x16000000`.

There are 3 + 1 sites, all in audio TUs (init_1AAE0, init_15550, init_214F0). Unloaded references
(`ROM offset << 5 | tag`) still fail the first test, because the tag sets the low bits. This is the
"address constants / K0_TO_PHYS" gap from P4; other shapes will need the same treatment as they
show up.

## 3. Audio HLE (`port/audio/`)

- **`aud_abi.c`** is a CPU interpreter for Conker's audio microcode, Rare's n_audio ABI. It uses the
  Conker/MP3 table:
  - 0 OVERLOAD, 1 ADPCM, 2 CLEARBUFF, 3 ENVMIXER, 4 LOADBUFF, 5 RESAMPLE, 6 SAVEBUFF;
  - 7/8 MP3 (counted, not implemented);
  - 9 SETVOL, A DMEMMOVE, B LOADADPCM, C MIXER, D INTERLEAVE, E filter (pole / IIR), F SETLOOP.

  DMEM is a 4 KB big-endian byte array. Every operand is relative to 0x4F0. Conker's own C code
  uses the fixed buffers 0x4E0/0x650 (dry L/R) and 0x7C0/0x930 (wet L/R) relative to 0x4F0. The
  resample table is read from the ucode data in the user's ROM (found at 0x2CD80). DRAM operands
  are wasm pointers; 24-bit-masked ones get the 0x10 top byte back, which is valid because the
  audio heap and buffers live in `n64_rdram` (0x102…–0x10A…).

  The semantics follow mupen64plus-rsp-hle as a behavioural reference only. Nothing was copied;
  see `port/audio/LICENSES.md`.
- **`aud_out.c`** holds a ring buffer and the SDL audio callback. It uses Emscripten's built-in SDL
  audio (`library_sdl.js`, Web Audio), because the pinned `conker-emsdk` image has no SDL2 port
  cached and the build must not download one. The calls are the SDL 1.2 subset that SDL2 also has,
  so switching to `-sUSE_SDL=2` only needs an `embuilder build sdl2` step in the image. In node
  (no AudioContext) the output is disabled.
- **Hooks** (`pc_os.c`):
  - `osSpTaskStartGo(M_AUDTASK)` → `aud_run_alist`;
  - `osAiSetNextBuffer` → the SDL ring;
  - `osAiSetFrequency` sets the rate.

  No audio task arrives yet: the audio thread `func_10009400` (C) waits for the scheduler
  `func_100049E0` (asm), and the audio manager init `func_10008180` / `func_10008F90` is asm too.

### Test path (`port/audio/aud_test.c`, vbe TU)

The test drives the game's C synthesizer directly:

1. `alHeapInit`;
2. `n_alInit` → `n_alSynNew`, with the config from func_10008180's asm: 0x2C/0x28/0x40 voices,
   2 fx busses of type 6 with D_8002B1A4's parameter tables, and 22020 Hz;
3. one sound record from the ROM bank, `n_alSynAllocVoice` + `n_alSynStartVoiceParams`;
4. `n_alAudioFrame` builds about 375 commands per 736 samples, including the reverb busses;
5. `aud_run_alist` runs them, and the result is checked and written to a WAV.

The DMA callback is a PC one (ROM → ring of 1 KB buffers), because the game's `func_100097CC`
needs the asm-initialised buffer lists.

**Sound bank layout** (asset table at 0xAB2240, walked as `func_1502AC88` does: entry *i* of a
table at `p` is `{s32 offset, u32 info}` and the child is at `p + offset`). The audio assets are
(0x17,0), (0x17,1), (0x17,2) and (0x17,3):

- (0x17,0) is the ctl, rzip, 'B1'. It has 1 bank with 170 instruments; only instrument 0 is in
  the ctl, and the others are encoded references.
- (0x17,1) holds the sound records, which Rare loads on demand through the asm `func_10009CBC`.
  A record is laid out as follows, with record-relative pointers; 1332 records were walked:
  - +0x00 ALSound
  - +0x10 ALEnvelope
  - +0x20 ALKeyMap
  - +0x28 ALWaveTable (its base is relative to (0x17,2))
  - +0x40 ALADPCMBook
- (0x17,2) is the sample table (21.6 MB).
- (0x17,3) is the 'S1' sequence bank.

**Result:**

```
AUDTEST=26390 port/web/boot.sh 8   ->  port/build/audio/audtest.wav
[audtest] 110400 frames: L rms 3957 peak 23022 nonzero 92%, diff/energy 0.360 -> PASS
[audtest] ops: adpcm 555 resample 600 envmix 600 loadbuf 11728 savebuf 14898 mix 17400 filter 2400
AUDTEST=28060:200 ...  -> rms 4233, diff/energy 0.024 -> PASS
```

White noise gives a diff/energy of about 2 and silence an rms of 0. As an independent check, a
Python VADPCM decoder of the same record (scratch script, not in the repo) gives the same
diff/energy values. Its **normalised cross-correlation with the WAV's left and right channels is
1.0000 at lag 0**, in windows at samples 8000, 20000, 50000 and 90000. So the C synth, the ADPCM,
envmixer, mixer, interleave and save paths, and the K0 rewrite produce the exact waveform.

Not verified: the resample path with pitch ≠ 1 (it does run on the fx busses), the reverb's audible
output (the wet amount is 0 for this voice), OVERLOAD, and the pole-filter variant. Browser playback
(`?app=game&audtest=26390`, then click the page) loads and waits for the click in headless Chrome,
but actual sound output has not been heard.
