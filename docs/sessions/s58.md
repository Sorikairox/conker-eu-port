## The frame puzzle: solved
The s57 drafts (`func_150CB2D0` & co.) had the stores right but the frame `ra 0x1C, hole 0x20-0x28, spill 0x28, struct 0x30-0xA8`
against the ref `ra 0x1C, spill 0x20, struct 0x28-0xA0, 8 free bytes 0xA0-0xA8`.

### IDO -O2 -g3 frame layout (measured on standalone test files, `docs/sessions/s58_drafts/frame_tests.c`, compiled by `cx.sh`)
From the bottom up:
1. outgoing args `0x00..` (max(0x10, 4 * args)), here 0x18 for the 6-arg `func_15132FBC`;
2. saved registers (ra at 0x1C for a 0x18 arg area);
3. **compiler temps** (spills of a call result live across another call; 8 bytes per temp), directly BELOW the locals;
4. **named locals, from the frame top downward in declaration order** (first declared = highest address; locals in registers still own a slot).
Frame = round8(args + saves + temps + locals); the rounding padding lands at the BOTTOM (between saves and temps), so the locals stay anchored at the top.
Measured: `S30 sp` (0x78) + one spill -> frame 0xA0, spill 0x20, struct 0x28; `S31` (0x7C) -> 0xA8, spill 0x24, struct 0x2C; `int pad[2]; S30 sp;` -> 0xA8, spill 0x20, struct 0x28 (= the ref layout).

### What the hole was
Bisecting the draft statement by statement (one function per removed statement, all in one file) showed two statements that each cost 8 bytes of temp area:
the spilled `func_150ADA20()` result (the real ref spill at 0x20) and **the chained float assignment `sp.u28[3] = sp.u28[2] = X;`**: IDO allocates an extra 8-byte temp
for the chain even though the final code keeps the value in `f2`. Mine therefore had 16 bytes of temps (spill at 0x28, dead temp at 0x20) and 0x78 bytes of locals; the ref has 8 bytes of temps and 0x80 bytes of locals.
So s57's pads/tails could never work while the chain was there (they grew the frame instead).

### Recipe
- Write the chain as two statements: `sp.u28[3] = X; sp.u28[2] = sp.u28[3];` (same `swc1 f2` x2, no temp). (`sp.u28[2] = X; sp.u28[3] = sp.u28[2];` was DIFF4: store order.)
- The struct is 0x80 bytes: 8 bytes of tail after `u9C` (`u8 padA0[0x8];`), or equivalently 8 bytes of named locals declared before it.
- Parameters: the stack args are read at m2c's offsets, so the signature needs all 15 slots: `(s32 arg0, s32 arg1, f32 arg2, f32 arg3, f32 arg4, s32 arg5, s32 arg6, s32 arg7, s16 arg8, s32 arg9, s32 argA, s32 argB, s32 argC, s32 argD, u8 argE)`.
- `void func_15143794(s16, s16, f32, void *);` above the function (s57), call `func_15132FBC(&sp, 3, 0xFF, 0, argE, 0)` with no prototype (header has none).
- Template: `docs/sessions/s58_drafts/spawner_template_func_150CB2D0.c`. Siblings differ only in literals (read them from the rodata words the asm carries once the file owns `.rodata`; `-149.0f` vs `-150.0f` cost a DIFF2) and the `u89` byte.
- Other notes: `u88` is `u8` when the ref stores 0xFF (`s8` gives `li -1`); `18.800001f` for 0x41966667; named f32 results live across calls stay in their home slots (no s-regs) and are declared ABOVE the struct (`func_150BB978`: `s16 spBE; f32 spB8, spB4, spB0, spAC;` then the struct).
- Other ruled-out layouts (for the record): two separate scalars before the struct gave +8 (a used named float costs another temp); a named `f32 temp_f2` for the chain value costs a 4-byte temp.
