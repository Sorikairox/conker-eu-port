## Key finding: the `(0, x)` comma flips commutative operand order
Session 46's "reversed order for two plain memory operands" rule is only half the story. When one operand is a named
local (or a call result held in a local) IDO does NOT keep source position reliably: `mem * local` and `local * mem` both
come out the same way. Wrapping the **local** operand in a comma expression, `(0, local)`, flips it. All four matches
use exactly this (each line carries `// fakematch:`):
- `func_15199200` / `func_1519C52C` (twins, `addu v0,v1,t9`): `p = idx * 0x24 + (0, temp_v1)` (0x28 for the twin), pointer form
  `(u8 *)(idx*0x24 + (0, temp_v1))` used inline for all three field reads, no `p` local.
- `func_151A23E4` (two `multu v1,t8`): `mem * (0, temp_v1)` for the last two products (`(0, temp_v1) * mem` or plain `mem * temp_v1` do not help).
- `func_151AAFFC` (`mul.s f6,f0,f4`, call result first): `f32 r = call(); r = mem90 + (mem94 * (0, r));`. Also the frame shape: `u8 **q = &arg0;`
  (arg0 reloaded from its home slot), `p = *q;` after the call, loads through `p`, then `p += 0x80; *(s32 *)(p + 8) = ...` with the
  stored value computed from `p + 8` / `p + 0xC` after the increment (offsets relative to the incremented p). The callee takes `u8`:
  pass `(x >> 16) - 0x40` with NO `& 0xFF` (otherwise the `andi t8; or a0,t8` pair is missing).
  The same recipe should fix the mul.s sibling `func_150EAA10` (slice below 0x130000, untried).
Search procedure that worked: write the expression with `(0, x)` on each operand in both positions plus the two plain orders, `tryall` them (8 at once).
