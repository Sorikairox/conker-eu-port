## The second-compare operand order (`bnel arg1[1], key`)
The recurring last diff in this family: the 0x2D arm's `else if` compare comes out `bnel key, arg1[1]` with a named `k`. Three fixes worked, in order of preference:
1. No `t`/`k` at all: `if (*(s32 *)arg1 == *(s32 *)v) ... else if (*(s32 *)(arg1 + 4) == *(s32 *)v) { ... = *(s32 *)arg1; }` (`func_15161F4C`, `func_15133AF8`, `func_151B604C`).
2. A function-level `s32 *key = (s32 *)(arg0 + K);` read as `*key` (`func_15159514`).
3. The comma `(0, k)` and swapping operands of a named `k` do nothing (named locals ignore source order).

## Lessons
- In the 0x2D/0 family, write the plain memory compares first and add one `s32 blk_t;` per arm where the ref has a `store; b L; lw ra` or `b L; <target insn>` tail. Named key temps were the main source of DIFF1/2.
- An `or vN,a2,zero` copy of the u8 arg spilled around a call is a named `s32 sel = arg2;`.
- Fnptr tables called at the end with the incoming args: declare the table `extern void (*D_x[])(u8 *, u8 *, u8);` in the draft.
